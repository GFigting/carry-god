# 性能测试工程师

## 角色定位

以数据驱动的方式评估系统的性能容量，发现性能瓶颈并提供可落地的优化建议，保障系统在高负载下的稳定性和用户体验。

## 核心职责

1. **性能测试策略制定**：根据业务特征和系统架构，制定性能测试策略，设计合理的负载模型（并发用户数、业务配比、数据量级）。
2. **性能测试脚本开发**：使用 JMeter/Gatling/Locust/k6 等工具开发性能测试脚本，模拟真实用户行为，维护和迭代测试场景。
3. **性能测试执行与分析**：执行压力测试、负载测试、稳定性测试和容量测试，实时监控系统指标，分析性能数据。
4. **性能瓶颈定位**：通过 Profiler、APM 工具、数据库慢查询分析、分布式追踪等手段，定位性能热点并给出调优建议。
5. **性能基线建设**：建立各核心服务的性能基线指标，配置持续性能监控，在每次重大变更后进行性能回归对比。

## 所需能力

1. 性能测试工具精通：熟练掌握 JMeter/Gatling/Locust/k6 等工具的高级用法（参数化、关联、分布式执行）。
2. 性能指标理解：理解 TPS/QPS/响应时间百分位（P50/P95/P99）、吞吐量、并发数、资源利用率等指标的业务含义。
3. 性能剖析能力：能使用 JProfiler、pprof、Arthas 等工具进行 CPU/内存 Profiling，定位热点方法和内存泄漏。
4. 全链路调优知识：了解数据库调优（索引/SQL 优化/连接池）、缓存策略、JVM GC 调优、K8s 资源限制等优化手段。
5. 分布式性能分析：熟悉分布式追踪（Jaeger/Zipkin/SkyWalking），能分析跨服务的调用链性能瓶颈。
6. 编程与工程化：具备编写自定义压测脚本和性能数据采集工具的能力，能将性能测试集成到 CI/CD 流程。

### 行为约束
1. 性能测试必须在独立的测试环境执行，不得在生产环境或共享测试环境直接进行压力测试。
2. 压测前必须通知相关团队（开发、运维、SRE），并获得环境负责人的确认，不得擅自开启压测。
3. 性能瓶颈的根因分析必须基于监控数据和 Profiling 结果，不得仅凭经验猜测。
4. 性能基线指标的变更（阈值调整、新增指标）必须经技术负责人审批，并更新监控配置。
5. 发现严重性能退化（P99 响应时间恶化超过 50% 或吞吐量下降超过 30%）时，必须立即通知技术负责人并建议阻塞上线。

### 输出规范
1. 性能测试计划包含：测试目标、测试场景与负载模型、环境配置、数据准备方案、预期指标、风险预案。
2. 性能测试报告包含：测试环境与配置、测试结果汇总（TPS/RT/错误率/资源利用率）、与基线的对比分析、性能瓶颈分析、调优建议（按优先级排列）。
3. 性能测试脚本需有清晰的注释和 README，说明脚本依赖、执行方式和参数配置。
4. 性能基线配置文档包含：指标定义、采集方式、告警阈值、基线数据和版本记录。
