# /withRequirement — 对话需求归集

## 触发

- `/withRequirement`
- `/withReq`
- `登记到目标总览`
- `填入目标总览`

## 适用范围

仅 TL 模式可用。若当前为 Teacher 模式，提示用户先执行 `/asTL`。

## 目的

把人类在当前对话中口述的一条或多条零散需求，按业务归属整理到 `A.目标体系/目标总览.md` 的既有 Goal 中，并按用户意图决定下一步是澄清、仅登记、计划落盘还是生成新对话推进提示词。默认情况下该指令只做需求登记，不创建任务、不写实施计划、不修改代码、不推进完成状态。

当用户叠加 `/withPlan`，或明确要求“分析后生成计划/按计划门禁输出文档/落盘实施计划”时，`/withRequirement` 升级为高级流水线：**需求分析 → 目标归属 → 最小充分登记 → 细节门禁 → 计划产物落盘**。计划仍必须保持 `in_review`，等待用户确认后才能实施。

升级后的核心原则是：**需求登记时就做可实施性分流。** 能明确落地的内容写成分点；影响实现路径但尚未确认的内容写成待确认；只有关键细节足够清楚的主题才返回 `/withGo /withPlan` 推进提示词。否则返回 `/withGrill` 或“补充口径后再推进”的提示词。

这样做的技术理由是：Agent 后续编码的输入越结构化、约束越完整，越能一次性完成局部搜索、方案设计和文件修改，减少反复补上下文、返工和大范围试探。

反模式：不要把 `/withRequirement` 做成“无条件补完目标总览”的文书工具。它必须先判断需求成熟度，只把确定信息简洁写入目标总览；缺失信息宁可进入 `待确认`，也不生成看似完整但偏离用户意图的内容。

## 与已有指令的边界

| 指令 | 处理对象 | 核心动作 |
|------|----------|----------|
| `/withRequirement` | 当前对话中的口述需求 | 自动分组、匹配既有 Goal、登记新子目标、返回推进提示词 |
| `/withGo` | 已定位的 Goal、既有子目标或已归属需求 | 判断成熟度，补齐子目标，并路由到澄清/计划/小修 |
| `/withPlan` | 已经足够清晰的实施主题 | 生成项目交付视角的实施计划，等待确认后才能开发 |
| `/withInbox` | `_需求收件箱/` 中的外部文件 | 分析外部材料、确认归属、移动归档 |
| `/withGrill` | 边界不清的需求 | 深度澄清业务规则和决策分支 |

## 执行流程

### Phase 1：提取与分组

1. 从用户本轮输入提取全部需求，不遗漏限制、后续设想和注意事项。
2. 先识别用户本轮真实意图：只分析、登记到目标总览、澄清问题、生成计划，还是准备后续实施。
3. 按项目、业务模块、页面入口和可独立推进主题分组。
4. 将“本期必须实现”“后续预留”“实施前必读”“待确认口径”分别识别，避免混写为同一完成项。
5. 初步判断每组需求是否具备实施前置细节：页面/入口、业务口径、数据来源、接口契约、权限、SQL/字段、验收边界。

### Phase 2：匹配 Goal

1. 读取 `A.目标体系/目标总览.md`。
2. 优先匹配已有 Goal 的目标效果、当前子目标和业务模块。
3. 检查是否已有语义相同或高度重叠的子目标：
   - 已存在且可承载：追加分点或检查项，不重复新建。
   - 同一 Goal 下是独立交付主题：使用下一个未占用序号新增子目标。
   - 跨 Goal：分别登记，不把多个业务域强塞进一个子目标。
4. 无法可靠匹配时停止写入该条需求，向人类说明候选归属；不得自行创建新 Goal。

### Phase 3：结构化登记

按实际复杂度使用最小充分结构。目标是让后续 Agent “知道要做什么”，不是把所有可能细节写满。

```markdown
- [ ] {序号}. {子目标一句话效果}
    - 总览：{页面、入口、业务效果和交付范围}
    - 分点：
        - [ ] {本期交付项}
    - 检查项：
        - [ ] {既有规范、IMPORTANT、兼容性或人工复查边界}
    - 待确认：
        - [ ] {公式、口径或范围不明确的问题}
```

规则：

- 保留用户原始业务意图和明确技术约束，不擅自扩展实施范围。
- 标题和总览必须清晰简洁；能一句话说清的不要展开成方案文档。
- 只写确定事实：用户明确说过、目标总览已有、项目文档/代码可验证。
- 推断、默认值、可能方案必须写入 `待确认`，不得混入 `分点` 或 `总览`。
- 后续设想写成“接口预留/后续扩展”，不得伪装成本期交付。
- 用户要求参考既有 UTIL、规范或组件时，写入检查项并保留准确入口；入口不明确时写“实施前定位并读取”，不臆造文件名。
- 不确定的公式、精度、空值、权限、分页或数据范围写入待确认。
- 不勾选 checkbox，不添加代码、SQL、部署或验证完成标签。

### Phase 4：可实施性分流

登记后按主题给出门禁结论：

| 结论 | 使用条件 | 输出倾向 |
|------|----------|----------|
| `可推进` | 业务口径、交付范围、关键技术边界基本明确 | 输出 `/asTL /withGo /withPlan ...` |
| `需澄清` | 公式、数据来源、权限、接口契约、验收标准等会影响实现路径 | 输出 `/asTL /withGrill ...` 或列出请用户补充的问题 |
| `仅登记` | 属于后续设想、预留能力或当前无可靠 Goal 归属 | 只登记或说明候选归属，不给开发提示词 |

不得为了让流程继续而把关键不确定项写成“默认按某方案实现”。如果确需采用假设，必须让用户在后续 `/withPlan` 前确认。

### Phase 5：计划衔接

若用户叠加 `/withPlan` 或明确要求生成计划文档，按以下规则处理：

1. 只有门禁结论为 `可推进` 的主题才能生成计划。
2. 按 `/withPlan` 和 `配置与元数据/产物工件规范.md` 创建 `ART-TL-实施计划.md`，状态为 `in_review`。
3. 计划正文必须基于项目交付视角，覆盖页面、按钮、接口、权限、SQL、数据结构和验证边界。
4. 计划中的 `待确认项` 必须保留为待确认，不得转写成已定方案。
5. 计划落盘后停止，等待用户确认；不得继续编码。

若主题为 `需澄清`，即使用户叠加 `/withPlan`，也先输出澄清问题或 `/withGrill` 提示词，不生成实施计划。

### Phase 6：输出推进提示词

按“一个 Goal 下可共同实施的同类主题一条对话”生成提示词。每条只占一行，格式为：

```text
/asTL /withGo /withPlan {GOAL 编号及分点}：{一句话推进目标}，先整理并落盘实施计划，等我确认后再开发。
```

需求明显复杂或跨前后端、接口设计、数据结构时，可追加 `/withReview`。存在关键业务口径未确认时，改用 `/withGrill`，不直接建议开发。

输出摘要必须包含：

- 写入位置：{Goal / 子目标 / 分点}
- 用户意图：{分析 / 登记 / 澄清 / 计划}
- 门禁结论：{可推进 / 需澄清 / 仅登记}
- 计划产物：{若已生成则列路径；否则写“未生成”}
- 下一步提示词：{单行；按门禁结论选择 /withGo /withPlan 或 /withGrill}

## 行为约束

### 必须做

- 一次处理用户本轮输入中的全部需求。
- 先判断用户真实意图，不把“请分析”误执行成“请补全文档/请写计划/请开发”。
- 先查重、再归属、最后编号。
- 保留本期范围、后续预留、规范入口和待确认项。
- 目标总览只做最小充分登记，宁可简洁，不做大段扩写。
- 完成后列出写入的 Goal / 分点、可实施性结论，并给出一行式推进或澄清提示词。
- 对影响代码结构、接口契约、SQL、权限或验收标准的待确认项，必须阻断开发建议，先引导澄清。
- 叠加 `/withPlan` 或用户明确要求计划时，满足门禁后必须按计划产物规范落盘实施计划。

### 禁止做

- 不创建、删除或改写 Goal 名称和目标效果。
- 不替人勾选完成状态。
- 默认不创建任务、计划、工作记录或产物；只有叠加 `/withPlan` 或用户明确要求计划产物时才创建实施计划。
- 不操作项目代码、SQL、Git 或部署状态。
- 不用该指令替代 `/withGrill`、`/withGo` 或 `/withPlan`。
- 不输出“直接开发/直接改代码”类提示词；清晰需求也应先经过 `/withGo`，复杂需求再经过 `/withPlan`。
- 不无条件补全目标总览，不把信息不足的需求包装成成熟需求。

## 与其他指令的交互

- **+ `/withGo`**：需求登记后，继续做成熟度判断、目标整理和下一步路由。
- **+ `/withGrill`**：登记时发现关键口径不清，先输出 grill 推进提示词。
- **+ `/withPlan`**：需求已清晰时，可在同一轮落盘实施计划；若不清晰则阻断计划，先澄清。
- **+ `/withReview`**：复杂需求的计划完成后派发独立审核。
- **+ `/withInbox`**：存在外部原始文件时使用 Inbox，不由本指令移动或处理文件。
