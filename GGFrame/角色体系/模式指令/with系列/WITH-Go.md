# /withGo — 目标理解与子目标拆解门禁

## 触发

- `/withGo`
- `/withGoal`
- `withGo`
- `withGoal`

## 适用范围

仅 TL 模式可用。若当前为 Teacher 模式，提示用户先执行 `/asTL`。

## 目的

`/withGo` 是所有目标执行开始前的高级门禁。它不只是“补全目标描述”，而是先判断用户输入和目标总览中的信息是否足以支撑后续动作，再选择：补齐既有 Goal 子目标、进入 `/withGrill` 澄清、进入 `/withPlan` 落盘计划，或在极小范围内建议直接小修。

升级后的核心原则是：**先确认细节，再写计划；先冻结口径，再改代码。** 如果业务规则、数据来源、页面入口、权限、接口契约、SQL/字段、兼容边界或验收口径仍不清晰，TL 不应把模糊项带入实施计划或编码，而应先输出待确认问题，或建议切换 `/withGrill` 做深度澄清。

这个约束不是流程负担，而是降低 Agent 执行成本的技术策略：提前把需求空间收敛为明确输入，可以减少后续反复读代码、重构计划、撤销改动和修补边界条件的 token 消耗。

`/withGo` 可以接收两类输入：

- **已落盘目标**：用户指定 `GOAL-XXX`、子目标或分点，TL 读取目标总览后做成熟度判断。
- **未落盘需求**：用户直接描述需求但未写入目标体系，TL 先按 `/withRequirement` 的归属和去重规则匹配既有 Goal，再做最小充分登记；无法可靠归属时停止写入并请用户确认。

`/withGo` 可以作为 `/withGrill` 和 `/withPlan` 的上位路由器：它先判断“现在缺什么”，再决定进入澄清、登记、计划或执行建议。它不能跳过这些门禁，也不能用自动补全制造“已经清楚”的假象。

这是树形目标体系的过渡版本：不新增真实树形数据结构，不调整既有序号规则，只把原“当前分点”的语义升级为“当前子目标”。子目标下的分点允许 Agent 与人共同维护建设。

## 概念定义

| 概念 | 定义 | 维护边界 |
|------|------|----------|
| Goal | 长期目标，仍由 `GOAL-XXX` 标识 | 人类维护目标名称和目标效果，AI 只读或按授权整理 |
| 子目标 | 原“当前分点”的升级语义，表示一个可交付主题 | 沿用原分点序号，AI 可在既有子目标下补充结构化分点 |
| 分点 | 子目标下的可执行检查项、交付项、验证项 | AI 可共同维护，需保留人类原始意图 |

## 执行流程

### Phase 1: 输入识别与目标定位

1. 读取 `A.目标体系/目标总览.md`。
2. 识别用户输入类型：
   - 已指定 Goal/子目标/分点：直接定位。
   - 未指定 Goal 但描述了需求：按项目、业务模块、页面入口、关键词匹配既有 Goal。
   - 无法可靠匹配：列出候选归属或要求用户补充 Goal 编号，不写入目标总览。
3. 读取该 Goal 的：
   - `目标效果`
   - `最近完成`
   - `当前子目标` 或兼容读取旧字段 `当前分点`
   - `挂起分点` 或 `挂起子目标`

### Phase 2: 需求成熟度判断

TL 先判断当前输入属于哪类成熟度：

| 成熟度 | 判定标准 | 后续动作 |
|--------|----------|----------|
| `线索` | 只有问题、想法或方向，没有明确页面/业务对象/交付结果 | 建议 `/withGrill` 或请用户补充，不写计划 |
| `需求草稿` | 有业务目标，但范围、规则、接口或验收边界不完整 | 最小登记到待确认，输出澄清问题 |
| `可计划需求` | 目标、范围、关键规则、交付面和风险基本明确 | 更新目标总览后，叠加 `/withPlan` 时落盘计划 |
| `可执行小修` | 范围极小、路径清晰、无需新增业务决策 | 可建议直接小修，仍不得越过用户指定的计划门禁 |

随后用 3-6 行概括：

- 目标要解决什么业务结果
- 当前最近完成到哪一步
- 用户本轮真正要求 Agent 做什么：只分析、登记、澄清、计划，还是准备实施
- 现在可继续推进的子目标有哪些
- 哪些内容存在不确定、阻塞或需要人工确认

### Phase 3: 子目标整理

对用户指定或当前最相关的子目标，整理为以下结构：

```markdown
- [ ] {序号}. {子目标一句话效果}
    - 总览：{涉及页面、入口、按钮、弹窗、接口、SQL 文件、数据结构的交付面}
    - 分点：
        - [ ] {可执行交付项}
        - [ ] {可执行交付项}
    - 检查项：
        - [ ] {IMPORTANT 重要逻辑、特殊业务校验、兼容性风险或自检要求}
    - 待确认：
        - [ ] {不确定内容；没有则省略}
```

**字段说明**：

- `总览`：从项目交付视角描述，不只写技术类名。
- `分点`：能被 Agent 或人逐项推进、验证、补充。
- `检查项`：记录 IMPORTANT 注释项、自检项、特殊校验规则、人工复查事项。
- `待确认`：不确定处直接留空或写明问题，不强行补全。
- 只写“用户已明确表达、目标总览已有、项目文档/代码可验证”的内容；推断内容必须标为“推断”或放入 `待确认`。

### Phase 4: 目标总览最小补充

在用户明确要求整理目标总览，或当前输入需要先落入目标体系才能继续计划时，TL 可以更新 `A.目标体系/目标总览.md`，但必须遵循“最小充分”原则：

1. 只在既有 Goal 下补充或整理子目标/分点；不创建新的长期 Goal。
2. 标题用一句话描述交付效果，避免把技术方案写进标题。
3. `总览` 只覆盖确定的页面、入口、接口、SQL、数据结构、权限和验证边界。
4. 缺失信息写入 `待确认`，不得用默认方案补齐。
5. 保留原序号、原始描述和人类意图；不勾选 checkbox。

### Phase 5: 细节确认门禁

整理或登记后，TL 必须判断当前信息是否足以进入 `/withPlan` 或编码。判断维度至少覆盖：

- **业务口径**：核心规则、计算公式、状态流转、异常/空值处理是否明确。
- **用户交互**：页面入口、按钮、筛选项、弹窗、列表列、表单字段、操作反馈是否明确。
- **接口契约**：接口路径、入参出参、分页/排序、权限点、错误提示和兼容策略是否明确。
- **数据结构**：表字段、字典/枚举、DO/VO/DTO、SQL 文件策略和历史数据处理是否明确。
- **验证边界**：人类验收方式、自动/手工验证重点、不可回归的既有场景是否明确。

门禁结论分三类：

| 结论 | 处理方式 |
|------|----------|
| `可计划` | 输出 `/withPlan` 推进指令，允许进入计划落盘，但计划仍需用户确认后才能实施 |
| `需澄清` | 只输出待确认问题，建议 `/withGrill` 或请用户补充，不输出编码指令 |
| `可小修` | 仅当范围极小且细节已充分时，允许建议 TL 直接执行；仍需说明验证边界 |

### Phase 6: 计划衔接

当用户叠加 `/withPlan`，或明确要求“生成计划/落盘计划/按计划门禁输出文档”时，`/withGo` 在门禁结论为 `可计划` 后继续执行 `/withPlan` 的计划产物规则：

1. 按 `配置与元数据/产物工件规范.md` 定位 `A.目标体系/GOAL-XXX/产物/{任务序号}/`。
2. 生成 `ART-TL-实施计划.md`，frontmatter 使用 `status: in_review`。
3. 计划内容只基于已确认信息和明确待确认项；不得把 `待确认` 写成已定方案。
4. 计划落盘后等待用户确认，禁止继续修改项目代码。

若门禁结论为 `需澄清`，即使叠加了 `/withPlan`，也不得落盘实施计划；只能输出澄清问题或生成 grill 推进提示。

### Phase 7: 门禁输出

整理完成后，口头输出：

```markdown
withGo 门禁已完成 — GOAL-XXX

- 目标理解：{一句话}
- 用户意图：{分析 / 登记 / 澄清 / 计划 / 实施准备}
- 需求成熟度：{线索 / 需求草稿 / 可计划需求 / 可执行小修}
- 当前子目标：{列出序号和标题}
- 已处理：{本次登记、整理或落盘了什么}
- 门禁结论：{可计划 / 需澄清 / 可小修}
- 待确认：{仍需人类确认的问题；没有则写“无”}
- 计划产物：{若已按 /withPlan 落盘，列出路径；否则写“未生成”}
- 建议下一步指令：{根据门禁结论给出；整条保持单行}
```

## 行为约束

### 必须做

- 先理解 Goal，再拆可执行分点
- 兼容旧标题 `当前分点`
- 保留原分点序号规则
- 不确定处留空或放入 `待确认`
- 先判断用户真实意图，不把“请分析”误执行成“请补全文档/请写计划/请开发”
- 对未落盘需求先做归属和去重，能可靠匹配既有 Goal 才写入目标总览
- 目标总览只做最小充分补充，不进行大段扩写
- 从项目交付视角写 `总览`：页面、按钮、弹窗、接口、SQL、数据结构、权限、IMPORTANT、自检边界
- 对复杂子目标建议继续叠加 `/withPlan`、`/withReview`
- 门禁输出末尾给出可直接复制的单行下一步指令；例如：`建议下一步指令：/asTL /withGo GOAL-101 P23 回归第 5 行、修复第 10 行草稿定位 Bug、核查第 14 行返修价格保底方案`
- 若存在会影响代码结构、接口契约、SQL、权限或验收标准的待确认项，必须先归为 `需澄清`，不得建议直接编码
- 对可计划事项，推进指令应优先包含 `/withPlan`；对关键口径未定事项，推进指令应优先包含 `/withGrill`

### 禁止做

- 不创建、删除 Goal
- 不无条件补全目标总览
- 不替人勾选目标或子目标完成状态
- 不强行重排全部目标序号
- 不把目标体系改造成真实树形目录或新数据结构
- 不在 Teacher 模式下执行 TL 目标推进
- 不用 `/withGo` 代替 `/withGrill`：需求不清仍应 grill；`/withGo` 只做目标理解和执行拆分
- 不把“待确认”伪装成“实施假设”继续改代码
- 不在用户只要求分析时自动落盘计划；只有叠加 `/withPlan` 或明确要求计划产物时才生成计划文档

## 与其他 with 指令的交互

- **+ `/withGrill`**：若子目标仍有关键问句或业务边界不明，先 grill，再回到 withGo 整理。
- **+ `/withPlan`**：withGo 先做成熟度和细节门禁；只有 `可计划` 时才按 withPlan 落盘实施计划。
- **+ `/withReview`**：review 审核的是实施计划；withGo 提供目标上下文。
- **+ `/withFinish`**：完成归一化后，可回看目标总览，将结果沉淀到子目标检查项或工作记录。

## 过渡期兼容

- `当前分点` 与 `当前子目标` 在过渡期等价。
- 新整理的 Goal 优先使用 `当前子目标`。
- 未整理的旧 Goal 不强制批量迁移，按使用时逐步升级。
