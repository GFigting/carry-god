# /withInbox — 需求收件箱处理

## 触发

- `/withInbox`、`处理收件箱`、`收件箱`、`看看收件箱` — TL 模式下触发需求收件箱处理

## 目的

将外部需求（文件夹级别，含原型图 HTML / 文档 / 截图等）从 `A.目标体系/_需求收件箱/` 中**体系化地接入框架**，转化为 Goal 分点或新建 Goal，写入目标总览。

---

## 核心立场：我们是开发者，不是文档翻译器

### 关键认知

外部文档中**经常混杂两类信息**：

| 类型 | 特征 | 真实度 | 示例 |
|------|------|--------|------|
| **业务语义** | 描述用户要做什么、解决什么问题 | 高（这是真实需求） | "开票时需要关联对账单" |
| **技术猜测** | 给出表名、字段名、模块划分、数据结构 | **极低（对方的认知产物，不是事实）** | "新建 `invoice_detail` 表，字段 `bill_id`、`amount`" |

**类比 SQL 注入**：如果 inbox 不加区分地把外部文档中的技术猜测当作事实来生成 Goal 和 grill，就像把用户输入当作 SQL 执行一样危险——错误的前提会污染整个后续设计链。

### Agent 的处理立场

处理收件箱时，Agent 必须持有以下立场：

1. **我方对此业务尚不了解**——以学习者的姿态进入，目标是理解业务
2. **外部文档 = 原始材料，信任度极低**——其中的表名、字段名、模块划分是对方基于自身认知的猜测，**不应直接作为我方设计的输入**
3. **从业务语义反推需求**——提取"用户要达成什么效果"，忽略"对方认为该怎么做"
4. **技术判断留给我方后续流程**——表结构、字段设计、模块归属由 `/withPlan` 和开发阶段确定，不由 inbox 阶段拍板

### 原始文件标注原则

- 收件箱中的**每一个文件都是原始文件**，Agent 必须在分析报告中明确列出
- Agent 对原始文件的总体信任度声明：**"技术细节不可信，业务方向可参考"**
- TL 在后续开发中应以**我方代码库的实际情况**为唯一真相来源，原始文件仅作业务背景参考

## 执行模型

```
用户: /withInbox
      ↓
Agent 扫描 A.目标体系/_需求收件箱/（排除 _已处理/ 和 README.md）
      ↓
逐个文件夹分析需求内容，分两层：
  【第1层】原始文件清单 — 列出该需求文件夹中每个文件，标注文件类型
  【第2层】业务/技术分离分析：
    ├── 提取纯业务语义：用户角色、操作场景、要达成的业务效果
    ├── 识别技术猜测：文档中出现的表名、字段名、模块划分、接口路径
    └── 标注信任度：业务描述（可信）vs 技术细节（极低信任，留待后续验证）
      ↓
搜索现有 GOAL 做去重和关联检查：
  - 读取 目标总览.md → 搜索语义相似的分点
  - 检查是否有已存在的相关 GOAL
      ↓
对每个需求，向用户输出分析报告：
  ├── 📋 原始文件清单（逐个列出，标注"原始文件，技术细节不可信"）
  ├── 🔍 业务语义提炼（用我方语言重述需求本质）
  ├── ⚠️ 文档中的技术猜测（表名/字段名/模块划分 — 仅供参考，不作为设计输入）
  ├── 🏠 归属建议：匹配现有 GOAL / 建议新建 GOAL / 无法判断需澄清
  └── 💡 建议 grills 聚焦方向（哪些业务点需要向需求方澄清）
      ↓
人类确认全部归属 → Agent 写入目标总览（纯业务语言描述，不写入技术猜测）
      ↓
原始需求文件夹移动到 _已处理/（保留追溯）
      ↓
口头询问：是否需要 `/withGrill` 对新分点做深度业务澄清？
  → 提醒：grill 的目标是理解业务本质，不是验证外部文档的技术细节
```

## 行为约束

### 必须做

- 扫描收件箱时排除 `_已处理/` 和 `README.md`
- 逐个分析需求文件夹的**全部内容**（.html / .md / .txt / .png / .xlsx 等）
- **对每个需求执行两层分析**：第1层列出原始文件清单，第2层做业务/技术分离分析
- **明确识别并标注文档中的技术猜测**：如果文档提到表名、字段名、模块划分、接口路径，必须标注为"对方技术猜测，极低信任度，不作为设计输入"
- **输出分析报告时列出原始文件清单**，并声明"以上均为原始文件，其中的技术细节（表名/字段名/模块划分）不可信，仅业务方向可参考"
- 分析完成后**口头列出所有需求摘要**（每个需求一句话概括），然后逐个建议归属
- 搜索现有 GOAL 做关联检查，避免重复创建
- **归集前必须获得用户确认**（不允许 Agent 自行写入目标总览）
- **Goal 分点描述使用纯业务语言**，不照搬外部文档中的表名、字段名等术语。如有疑问用业务语言描述疑问，如"需要确认XX业务概念在我方系统中如何落地"而非"需要确认是否有XX表"
- 处理完成的需求文件夹移动到 `_已处理/`（保留追溯，不直接删除）
- 写入目标总览后，口头建议用户是否需要 `/withGrill` 对新分点做深度业务澄清，**同时提醒 grill 的方向是理解业务本质，不是验证外部文档的技术细节**
- 记录本次处理的简要日志

### 禁止做

- 不在用户确认前写入或修改 `目标总览.md`
- 不修改需求文件夹中的原始内容
- 不删除原始需求文件夹（移动到 `_已处理/` 即可）
- 不在 Teacher 模式下响应此指令
- **不将外部文档中的表名、字段名、模块划分直接写入 Goal 分点**（这些是对方猜测，不是需求）
- **不以外部文档的技术细节为依据判断需求可行性**（技术评估留待 `/withPlan` 阶段，基于我方代码库实际情况）

## 归集格式

### 新建 GOAL

在 `目标总览.md` 中追加：

```markdown
## GOAL-NNN: {项目缩写}-{目标名}

- **目标效果**：{从业务语义提炼的一句话效果，纯业务语言}
- **最近完成**：
- **当前分点**：
    - [ ] 1. {需求核心点简述，纯业务语言，不含外部文档的技术猜测}
- **原始文件**：
    - `{需求文件夹名}/` — 共 {N} 个原始文件（{文件类型列举}）
    - ⚠️ 以上为外部提供的原始文件，其中涉及的表名、字段名、模块划分等技术细节**极不可信**，仅为理解业务方向参考。技术方案以我方代码库实际情况为准。
```

- GOAL 编号取当前最大 GOAL 编号 +1（跳过 002 等已占用编号）
- `{项目缩写}` 从项目注册表匹配；若无法确定，询问用户
- 分点描述必须使用**纯业务语言**——描述"要达成什么业务效果"，不写"建什么表"、"加什么字段"。外部文档若包含数据模型设计，应提炼为业务需求后重述，不直接引用其表名/字段名

### 追加到现有 GOAL

在对应 GOAL 的 `当前分点` 下追加：

```markdown
    - [ ] {序号}. {需求核心点简述，纯业务语言} | 来源：收件箱 `{需求文件夹名}/`（原始文件 {N} 个，技术细节不可信） | {日期}
```

### 原始文件标注规范

无论新建 GOAL 还是追加分点，归集时必须包含：
1. **原始文件夹名**（可追溯）
2. **文件数量 + 类型概要**（.md / .html / .png / .xlsx 等）
3. **信任度声明**：明确告知 TL "技术细节极不可信，业务方向可参考"

## 从 inbox 到 grill 的聚焦原则

当收件箱处理后建议执行 `/withGrill`，Agent 必须遵循以下聚焦原则：

### grill 的正确方向：理解业务本质

- 问的是"什么用户在什么场景下要达成什么效果"
- 问的是"业务规则是什么"（什么条件下触发、什么数据范围、什么约束）
- 外部文档提到表名/字段名时 → 转化为业务问题："这个业务概念在我方系统中目前是如何表达的？是否有对应的数据来源？"
- 外部文档提到模块划分时 → 转化为归属问题："这个功能在业务上属于哪个领域的职责？"

### grill 的错误方向：验证外部文档的技术细节

- ❌ "外部文档提到 `invoice_detail` 表，是否确认新建此表？"
- ✅ "开票明细数据目前在我方系统中是否有来源？如果有，是哪个模块/接口？"
- ❌ "外部文档设计了 `bill_id` 字段，字段类型是否按文档来？"
- ✅ "开票与对账单的关联关系是什么？一对一还是一对多？关联键是什么业务标识？"

### 具体做法

Agent 在生成 grill 问题时：
1. 先扫描外部文档中的技术猜测（表名/字段名/模块名）
2. 将每个技术猜测**翻译为业务问题**——"这个技术名词背后，对方想表达什么业务概念？"
3. 以"我方系统如何支撑这个业务概念"的角度提问
4. grill 明细文件中不引用外部文档的技术名词（除非先在问题中注明"外部文档建议了XX，请确认业务实质"）
