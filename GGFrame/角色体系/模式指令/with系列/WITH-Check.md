# /withCheck — 纯代码规范检查

## 触发

- `/withCheck` — 显式触发，TL 口述改动范围，Agent 判定维度后派发检查
- 隐式触发：`/withFinish` 步骤 2 内部委托 `/withCheck` 执行质量检查

## 适用范围

**仅 TL 模式可用**。若当前为 Teacher 模式，提示用户先执行 `/asTL`。

## 目的

在测试前、提交前，对代码变更做**纯模式层面的合规检查**。检查者无业务理解，仅对照框架约定的规则做语义匹配——不会因为"这个代码看起来和业务逻辑不符"而误报，也不会因为"这个写法虽然丑但业务上是对的"而漏检。

**可叠加于**：任意开发阶段——写完一批代码后、`/withTest` 前、`/withFinish` 前均可触发。

## 核心原则

- **只对模式，不对业务**：检查者不判断业务是否正确，只判断代码是否遵守项目约定
- **TL 描述，Agent 判定**：TL 口头说做了什么 → Agent 分析涉及哪些检查维度 → 派发
- **规则全在检查清单**：检查维度硬编码于 `CHK-项目代码质量自检.md`，不依赖 Agent 常识

## 执行流程

```
TL 触发 /withCheck [可选：口述改动范围]
    │
    ├── Step 1 — TL 提供改动上下文
    │   Agent 引导 TL 口头描述：
    │   - 改了什么文件（大致范围即可，不必精确到行）
    │   - 变更类型（新增接口 / 修改查询 / 导入导出 / DDL / 字典 / 常量 / 数据结构 等）
    │   - 涉及的技术类型（Mapper/Service/Controller/VO/DO/Entity/Job/SQL）
    │
    ├── Step 2 — Agent 判定检查维度
    │   自动匹配 CHK-项目代码质量自检 的维度：
    │   - 改动含 Mapper/Service → 启动维度1 (Mapper/Repository)
    │   - 改动含新数字/字符串字面量 → 启动维度2 (常量管理)
    │   - 改动含异常抛出 → 启动维度3 (异常处理)
    │   - 改动含字典/DictType → 启动维度4 (字典维护)
    │   - 改动含导入/导出/上传/文件处理 → 启动维度5 (特殊功能)
    │   - 改动含 DDL/DO/Entity/数据库投影VO → 启动维度7 (数据结构字段分组)
    │   口头列出选中的维度，用户确认（可选跳过不适用维度）
    │
    ├── Step 3 — 派发 QA-004 代码质量检查员
    │   subAgent 收到：
    │   - 改动文件列表（或范围描述）
    │   - 选中的检查维度
    │   - 项目 docs/ 中的规范文件路径
    │   - 强制约束：「禁止检查业务逻辑，只检查代码模式」
    │
    ├── Step 4 — subAgent 执行检查
    │   - 读取 CHK-项目代码质量自检.md → 逐维度逐项核验
    │   - 读取项目 docs/ 中的对应规范文件
    │   - 对每个改动文件逐行扫描
    │   - 输出：通过/不通过 + 问题位置 + 违规项 + 修复建议
    │
    └── Step 5 — TL 修复 + 复检
        若通过 → 流程结束，口头报告
        若不通过 → TL 修复违规项 → 可再次 /withCheck
```

## 行为约束

### TL 必须做

- 提供改动范围描述（文件列表或范围描述）
- 对 Agent 选中的检查维度做口头确认
- 收到检查报告后修复违规项（如存在）

### Agent 必须做

- 主动判定涉及维度，不要求 TL 手动列出
- 在检查 prompt 中强调「禁止检查业务逻辑，只检查代码模式」
- 将检查报告写入 `A.目标体系/GOAL-XXX/产物/{任务序号}/`
- 口头报告检查结论

### subAgent 必须做

- 逐项对照检查清单核验，不遗漏
- 仅检查代码模式（写法/结构/命名），不判断业务正确性
- 对不确定的项标记「需人工确认」，不强行判定
- 输出格式遵循 CHK-项目代码质量自检.md 的输出规范

### 禁止做

- 不得检查业务逻辑正确性
- 不得检查架构设计合理性（那是 `/withReview` 的事）
- 不得修改代码（只出具报告）
- 不得在 Teacher 模式下使用

## 维度判定规则

Agent 按以下规则自动判定涉及的检查维度：

| 维度 | 触发条件（满足任一即启动） |
|------|-------------------------|
| 1. Mapper/Repository | 改动涉及 `*Mapper.java`、`*Mapper.xml`、`*ServiceImpl.java` 中的数据库访问（查询/更新/批量操作） |
| 2. 常量管理 | 改动中新增了裸数字/字符串字面量（非注解值、非日志消息） |
| 3. 异常处理 | 改动中新增了异常抛出语句（`throw`）或错误码引用 |
| 4. 字典维护 | 改动涉及 `DictTypeConstants` 或新增字典 SQL |
| 5. 特殊功能 | 改动涉及 `EasyExcel`/`MultipartFile`/`InputStream`/`HttpServletResponse`/文件读写 |
| 6. 代码注释与可审核性 | 改动涉及 Controller/@FeignClient/Service 接口（新增/修改公共方法），或新增方法满足"重要方法判定规则"（R1-R8），或改动文件数 ≥ 3（可能存在需检查注释的重要方法） |
| 7. 数据结构字段分组与可审核性 | 改动涉及 DDL、`*DO.java`、`*Entity.java`、`*DataObject.java`，或直接承载 Mapper 查询结果/数据库投影/导入导出明细的 VO/DTO |

**维度跳过规则**：若项目缺少某维度的规范文档（如无可用的规范文件），该维度标记为「跳过 — 项目未定义规范」，不视为不通过。

## 与 `/withFinish` 的关系

- `/withFinish` 步骤 2 「代码质量检查」内部委托给 `/withCheck` 执行
- `/withFinish` 触发时若检测到代码变更 → 自动走 `/withCheck` 流程 → 通过后继续 `/withFinish` 后续步骤
- `/withCheck` 可独立触发（如 `/withTest` 之前想先跑一遍检查）
- `/withCheck` 不能替代完整的 `/withFinish`（不做知识归集、不提交代码、不更新工作记录）

---

## 与其他指令的交互

- **+ `/withPlan`**：`/withCheck` 可在计划阶段就触发——在编码前对现有代码做基线检查
- **+ `/withTest`**：建议 `/withCheck` 在 `/withTest` 之前执行，避免测试计划基于有问题的代码
- **+ `/withFinish`**：`/withFinish` 自动调用 `/withCheck`，无需单独声明
