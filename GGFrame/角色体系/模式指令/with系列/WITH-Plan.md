# /withPlan — 强制计划先行

## 触发

- `/withPlan` — 在 TL 模式下启用计划先行约束

## 作用

将 CLAUDE.md 中"计划产物先行"规则提升为**强制执行门禁**。当用户声明 `/withPlan` 后，TL 在任何设计工作完成后、代码修改前，**必须**将改动计划落盘为产物工件。

## 行为约束

### 必须做

1. TL 完成设计/方案分析后，**必须**先将计划写入产物工件
2. 计划文件路径：`A.目标体系/GOAL-XXX/产物/{任务序号}/[GOAL{NNN}]-[{任务序号}-{子序号}-{产物序号}]-ART-TL-实施计划.md`
3. 计划 frontmatter 使用 `status: in_review`
4. 计划正文包含：目标、范围、项目交付视角的关键改动、测试/验证策略、假设与待确认项
5. 向用户口头汇报摘要 + 文件路径
6. 等待用户明确确认（"确认""按这个做""继续"等）后，才能进入实施

### 计划内容要求 ⚠️ 强制

计划不能只按技术动作罗列文件和类名，必须基于项目交付视角描述修改，让人类能直接判断业务页面和数据结构影响：

- **前端页面变化**：新增或修改哪些页面入口、菜单、路由、按钮、筛选项、弹窗、表单字段、列表列、操作区或导入导出能力。
- **后端能力变化**：新增或修改哪些接口、服务能力、权限点、菜单 SQL、字典、编码规则或定时/同步逻辑。
- **数据结构变化**：新增或修改哪些表、字段、索引、字典/枚举、DO/Entity、数据库交互 VO/DTO、接口入参出参；涉及字段时说明分组和业务含义。
- **SQL 处理方式**：说明本轮会新增哪些 SQL 文件；历史 SQL 默认不修改，只有人类明确允许或需要把多个 SQL 汇集成一份时才回改既有 SQL。

### 禁止做

- **禁止**在计划落盘前修改任何代码
- **禁止**将计划直接标记为 `approved`（必须用户确认）
- **禁止**以"改动太小"、"已经说清楚了"为由跳过计划落盘

### 例外

若用户明确表示"只要口头讨论"、"不需要落盘"或"先脑暴一下"，TL 可以仅口头输出草稿，不创建计划产物，但需在回复中明确标注"未归档草稿——尚未落盘，后续如需实施请先确认计划"。

## 产物

| 文件 | 路径 | 状态 |
|------|------|------|
| 实施计划 | `A.目标体系/GOAL-XXX/产物/{任务序号}/[GOAL{NNN}]-[{任务序号}-{子序号}-{产物序号}]-ART-TL-实施计划.md` | `in_review` |

## 与 `/withPlan` 未启用时的区别

| 场景 | 未启用 `/withPlan` | 启用 `/withPlan` |
|------|-------------------|-----------------|
| 用户说"帮我设计一个方案" | TL 自行判断是否需要落盘 | TL **必须**落盘计划 |
| TL 主动做设计 | TL 自行判断 | TL **必须**落盘计划 |
| 小改动 | TL 可直接动手 | TL 仍需落盘（即使是精简版） |

## 与其他指令的交互

- **+ `/withReview`**：计划落盘 → `/withReview` 派发审核 → 审核报告 + 计划一并呈现用户 → 确认后实施
- **+ `/withTest`**：计划落盘 → 用户确认 → TL 实施 → `/withTest` 在实施后派发测试计划
- **+ `/withMock`**：计划落盘 → 用户确认 → TL 实施 → `/withTest` 生成测试计划 → `/withMock` 基于测试计划生成数据
- **典型流水线**：`/withPlan /withReview /withTest /withMock` → 计划先行 → 独立审核 → 测试计划 → 测试数据
