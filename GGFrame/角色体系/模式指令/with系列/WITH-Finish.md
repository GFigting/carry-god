# /withFinish — 完成归一化

## 触发

- `/withFinish GOAL-XXX P{N}` — 显式声明 Goal 和分点，执行完成协议
- 自然语言 `完成了`、`做完了`、`收尾` + 上下文可推断 Goal 和分点 — 等价触发

## 目的

将"人类判断完成，AI 执行完成"规范化。人类完成开发后不再需要额外说明"帮我归档知识、提交代码"——`/withFinish` 一个指令完成所有收尾动作。

## 核心约束 ⚠️ 强制

**必须指定 GOAL + 具体分点。** 以下情况 Agent 必须**阻断**并提示用户补全：

| 输入 | 行为 |
|------|------|
| `/withFinish goal101` | **阻断** — "缺少分点编号，请指定如 `/withFinish goal101 P3`" |
| `/withFinish P3` | **阻断** — "缺少 Goal 编号，请指定如 `/withFinish goal101 P3`" |
| `/withFinish` 无上下文 | **阻断** — 询问 Goal 和分点 |
| `/withFinish` + 上下文可推断 | **放行** — Agent 口头确认推断结果后执行 |
| `/withFinish goal101 P3` | **放行** — 直接执行 |

**上下文推断规则**：若对话中已明确当前正在处理的 Goal 和分点（如工作记录中已有、或刚完成一个分步），Agent 可以推断，但必须口头确认（如"当前上下文为 GOAL-101 P3，确认执行完成协议？"）。

## 行为约束

### 必须做（完成协议六步）

**1. 知识归集**
- 扫描本次对话/任务文件中产生的技术决策、业务规则、SQL 变更、踩坑记录
- **项目级**：检查并更新项目 `docs/` 中的 README.md 快速定位区、业务文档（biz-*.md）中的业务描述准确性
- **通识级**：提炼可复用的知识 → 写入知识库根路径（从 `配置与元数据/框架设置.yaml` 读取 `knowledge.root_path`）对应子目录
- 使用 `tpl-knowledge` 模板，标注 `source` 为当前 Goal 和任务
- 口头输出归集清单：「本次归集 X 条知识」

**2. 代码质量检查（如有代码变更）→ 委托 `/withCheck`**

- TL 整理改动范围：文件列表 + 改动意图描述
- **自动委托** `/withCheck` 执行纯代码规范检查（详见 `WITH-Check.md`）：
  - Agent 接收改动范围 → 判定检查维度 → 派发 QA-004 子代理 → 对照 `CHK-项目代码质量自检` 逐项核验
  - 检查报告写入 `A.目标体系/GOAL-XXX/产物/{任务序号}/`
- **若通过** → 进入步骤 3 代码提交
- **若不通过** → TL 修复违规项 → 人工确认 → 重新检查（通过后进入步骤 3）
- 若本次无代码变更（纯分析/设计/文档），跳过此步骤，口头标注「本次无代码变更，跳过质量检查」

**3. 代码提交（如有代码变更）**
- 执行 `git add` + `git commit`
- Commit message 格式：`{项目缩写}-{模块名}-{功能描述}`（中文）
- 记录 hash + 时间到工作记录

**4. 工作记录更新**
- 在 `A.目标体系/GOAL-XXX/工作记录.md` 标记当前分步为 `[x]`
- 更新顶部状态摘要块（已完成数 +1、最近完成、下一个待执行）
- 更新 frontmatter `updated` 字段为当前日期（`YYYY-MM-DD`）
- **多维度完成检查**：扫描当前分点的维度标签（`【代码:*】【SQL:*】【部署:*】【配置:*】【验证:*】【数据:*】`）：
  - 若所有维度均已处于终态（代码已提交 / SQL 已执行或已验证 / 部署已发布 / 验证已验证 / 配置已生效 / 数据已迁移），标注「全维度完成」
  - 若存在未达终态的维度，口头列出并建议处理：如「分点 P5 代码已提交但 SQL 尚未执行、尚未部署，是否继续？」
  - 人类确认后继续——人类可能有意延后某些维度
- **执行仪表盘更新**：若当前 GOAL 满足仪表盘触发条件（见 AS-TL.md），刷新工作记录中的执行仪表盘矩阵

**5. 口头总结**
- 本次完成内容摘要
- 多维度完成状态（各维度终态确认）
- 知识归集清单
- 代码质量检查结果（如有）
- Git 提交摘要（如有）

**6. Agent 反馈收集（询问）**
- 口头询问：「本次是否有框架改进反馈需要记录？」
- 如有 → 按 `通用能力层/工具手册/UTIL-Agent反馈协议.md` 追加到相关框架文件
- 如无 → 跳过

### 禁止做

- 不得在 Goal 和分点不明确时执行
- 不得跳过知识归集扫描（即使结果为零也要报告"本次无新知识产生"）
- 不得在 Teacher 模式下使用（with 系列仅 TL 可用）

### 知识归集决策矩阵

| 来源 | 提取内容 | 归档位置 |
|------|---------|---------|
| 新增 SQL / 表结构变更 | DDL、表说明、索引设计 | 项目 docs/ 或 知识库 `技术文档/数据库/` |
| 新增业务规则 | 规则描述、触发条件、处理流程 | 项目 docs/biz-*.md 或 知识库 `业务领域/` |
| 技术踩坑 / 陷阱 | 问题现象、根因、解决方案 | 知识库 `经验教训/` |
| 可复用设计模式 / 约定 | 正例+反例代码、适用边界 | 知识库 `最佳实践/` |
| 技术选型 / 对比 | 方案对比、选型理由 | 知识库 `技术调研/` |
| 接口 / 页面新增 | 更新 README.md 快速定位区 | 项目 docs/README.md |

### 无变更时的行为

若本次完成的分步无代码变更、无新知识产生（如纯分析/设计讨论），Agent 仍需：
1. 标记工作记录分步完成
2. 口头报告"本次无代码变更，跳过质量检查；无新知识归档"
3. 执行工作记录状态摘要更新

## 产物

| 文件 | 路径 | 说明 |
|------|------|------|
| 知识归档文档 | `{knowledge.root_path}/{子目录}/` | 如有新知识产生 |
| 项目 docs 更新 | 项目 `docs/` | 如有业务/SQL 变更 |
| 代码质量检查报告 | `A.目标体系/GOAL-XXX/产物/{任务序号}/` | 如有代码变更 |
| Git commit | 项目仓库 | 如有代码变更 |
| 工作记录更新 | `A.目标体系/GOAL-XXX/工作记录.md` | 每次执行 |

## 与其他指令的交互

- **+ `/withPlan`**：不影响——`/withFinish` 是完成节点，`/withPlan` 是开始门禁
- **+ `/withTest` `/withMock`**：`/withFinish` 执行时会检查测试产物是否存在，口头提醒但不会阻断
- **+ `/mgmtReport`**：管理报告中可引用 `/withFinish` 产生的工作记录更新
