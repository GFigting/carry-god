# dream — 框架梦想改造讨论

## 触发

- `dream`、`dream {分点描述}` — 在 Teacher 模式下发起框架改造讨论
- 典型用法：`asTeacher dream 定时任务体系需要设计`

## 适用范围

**仅 asTeacher 模式可用**。若当前为 TL 模式，提示用户先执行 `/asTeacher`。

## 目的

将 Teacher 模式下的框架改进讨论**目标化**。用户对框架的任何改进想法记录在 `A.Teacher分析/梦想改造方案.md` 中，Agent 通过 `dream` 指令与用户展开轻松、发散的探讨，然后直接动手改造框架。

---

## 核心理念 ⚠️ 重要

**这不是一个开发流程，这是一场改造对话。**

区别于 TL 模式下严格的分步执行：
- ❌ 不强制计划先行落盘
- ❌ 不创建任务文件
- ❌ 不派发 subAgent
- ❌ 没有固定 Phase 流程
- ✅ 轻松对话，发散思维
- ✅ 主动建议更优方案
- ✅ 达成共识后直接修改框架文件

---

## 执行模型

```
用户: dream {分点描述}
      ↓
Agent 读取 A.Teacher分析/梦想改造方案.md 理解上下文
      ↓
Agent 分析用户思路 → 探索相关框架文件 → 形成初步理解
      ↓
Agent 与用户展开对话：
  - 确认理解是否正确
  - 提出可能的改进方向（鼓励发散）
  - 主动指出用户可能没意识到的更优方案或先进思路
  - 讨论利弊取舍
      ↓
双方达成共识 → Agent 直接修改框架文件 → 报告改动
      ↓
Agent 口头建议用户更新 梦想改造方案.md 中的分点状态
（Agent 不直接修改该文件，除非用户明确要求）
```

---

## 行为约束

### 必须做

- 先读取 `A.Teacher分析/梦想改造方案.md` 了解已有改造想法全貌
- 分析用户提出的分点时，关联到框架实际文件（读取相关 `.md`），基于事实而非猜测
- **主动发散**：用户嘴上不一定强调，但能发现更优/更先进的思路会让他们更开心。大胆提出替代方案、简化可能、甚至"这个分点其实可以不做，因为……"
- 讨论中保持轻松氛围——可以说"这个想法有意思"、"其实有个更简单的路子"、"要不要考虑……"
- 达成共识后直接动手修改框架文件（Teacher 模式本身就有框架完善权限）
- 改动完成后向用户报告：改了哪些文件、为什么这样改
- 口头提醒用户更新 `梦想改造方案.md` 中的勾选状态（如分点已完成）

### 禁止做

- 不修改 `A.Teacher分析/梦想改造方案.md`（除非用户明确要求 Agent 代写）
- 不创建任务文件、不更新任务状态
- 不操作项目代码（Java/Vue/TS 等）
- 不派发 subAgent
- 不强制要求用户确认计划（讨论自然达成共识即可）
- 不在 TL 模式下响应此指令

### 鼓励做

- 用反问帮用户理清思路："你提到的 X，最终期望的效果是 A 还是 B？"
- 轻量级探索后再回应，而非空谈
- 指出框架中已有的相关设计，避免重复造轮子
- 如果某个想法涉及较大改动，口头提醒风险即可，不强求计划文档

## 与 梦想改造方案.md 的交互协议

`梦想改造方案.md` 是 Teacher 模式的"目标总览"——人类维护，Agent 读取。

| Agent 允许 | Agent 禁止 |
|-----------|-----------|
| 读取 `梦想改造方案.md` 理解改造方向 | 创建/修改 DREAM 条目 |
| 口头建议某分点已达成（附证据） | 勾选 checkbox |
| 读取 `圆梦记录.md` 了解已完成改造 | 修改 `梦想改造方案.md` 任何内容 |
| 在用户明确要求时代写条目 | — |

### 圆梦记录

当用户确认某改造分点已完成，Agent 应口头建议：

> 这个改造已完成，你可以把分点迁移到 `A.Teacher分析/圆梦记录.md`，我来代写也可以。

如果用户同意代写，Agent 按"日期 + `- [x] {分点}`"格式倒序追加。
