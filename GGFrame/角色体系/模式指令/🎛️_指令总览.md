# 模式指令体系

## 概述

模式指令是控制主会话行为的**开关、增强器和管理命令**，分为四个系列：

| 系列 | 语义 | 关系 | 可用范围 |
|------|------|------|---------|
| **as 系列** | 模式切换 | 互斥（同一时间只能一种模式） | 全局 |
| **fw 系列** | 框架管理命令 | 独立触发（执行后返回当前模式） | 仅 Teacher 模式 |
| **with 系列** | 行为增强 | 可叠加（多个 with 同时生效） | 仅 TL 模式 |
| **mgmt 系列** | 管理分析 | 独立触发（执行后返回当前模式） | TL + Teacher 通用 |

## 人用指令入口

面向人的“快速选择”和四个系列使用明细已集中到 [[🏠_总览#指令速查|全框架总览 · 指令速查]]。本页保留 Agent 加载协议、模式检查和典型场景，完整执行规则仍以各指令定义文件为准。

## Agent 加载协议 ⚠️ 核心

### 渐进式加载原则

**指令定义文件不在启动时预加载**。Agent 仅在检测到触发词时才读取对应文件。

### 触发检测规则

```
用户输入
│
├── 包含 /asTL → 立即读取 as系列/AS-TL.md → 切换模式
├── 包含 /asTeacher 或 "教学模式" → 立即读取 as系列/AS-Teacher.md → 切换模式
├── 包含 /frameworkInit 或 "初始化引导" → 检查当前模式 → 若为 Teacher → 读取 fw系列/FW-FrameworkInit.md → 执行引导
├── 包含 /frameworkClean 或 "重置框架" → 检查当前模式 → 若为 Teacher → 读取 fw系列/FW-FrameworkClean.md → 执行重置
├── 包含 /frameworkRefresh 或 "框架刷新" 或 "刷新框架" 或 "同步目标" → 检查当前模式 → 若为 Teacher → 读取 fw系列/FW-FrameworkRefresh.md → 执行刷新
├── 包含 dream（且当前为 Teacher 模式）→ 读取 fw系列/FW-Dream.md → 进入改造讨论
├── 包含 /withGo 或 /withGoal 或 withGo 或 withGoal → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Go.md → 执行目标理解与子目标拆解
├── 包含 /withRequirement、/withReq、"登记到目标总览" 或 "填入目标总览" → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Requirement.md → 执行对话需求归集
├── 包含 /withGrill → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Grill.md → 执行目标澄清
├── 包含 /withPlan → 检查当前模式 → 若为 TL → 检查 withGo/grill 门禁 → 读取 with系列/WITH-Plan.md → 叠加约束
├── 包含 /withReview → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Review.md → 叠加约束
├── 包含 /withTest → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Test.md → 叠加约束
├── 包含 /withMock → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Mock.md → 叠加约束
├── 包含 /withQuery → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Query.md → 执行口语→JSON 查询条件生成
├── 包含 /withCheck 或 "代码检查" "规范检查" "代码自检" → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Check.md → TL描述改动→Agent判定维度→派发检查
├── 包含 /withAnnotate 或 "分析标记" "注释补全" "分析IMPORTANT" → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Annotate.md → 扫描IMPORTANT TODO→分析→穿透→标记转换
├── 包含 /withInbox 或 "处理收件箱" "收件箱" "看看收件箱" → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Inbox.md → 执行收件箱处理
├── 包含 /withOutbox 或 "导出需求" "需求导出" "打包需求" "导出给外部" → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Outbox.md → 执行需求导出
├── 包含 /withFinish 或 "完成了" "做完了" "收尾" → 检查当前模式 → 若为 TL → 读取 with系列/WITH-Finish.md → 执行完成协议
├── 包含 /mgmtReport 或 "日报" "周报" "月报" → 读取 mgmt系列/MGMT-Report.md → 执行报告生成（TL/Teacher 通用）
├── 包含 /mgmtEstimate 或 "工时汇总" "工时估算" → 读取 mgmt系列/MGMT-Estimate.md → 执行工时汇总（TL/Teacher 通用）
└── 包含多个指令（如 /asTL /withPlan /withReview /withTest）→ 从左到右依次加载
```

### 模式检查规则

```
with 指令触发时：
├── 当前为 TL 模式 → 正常加载
└── 当前为 Teacher 模式 → 提示"with 系列仅 TL 模式可用，请先 /asTL"

fw 指令触发时：
├── 当前为 Teacher 模式 → 正常加载
└── 当前为 TL 模式 → 提示"fw 系列仅 Teacher 模式可用，请先 /asTeacher"

dream 触发时（fw 系列特殊指令）：
├── 当前为 Teacher 模式 → 读取 FW-Dream.md → 进入改造讨论
└── 当前为 TL 模式 → 提示"dream 仅 Teacher 模式可用，请先 /asTeacher"

mgmt 指令触发时：
├── 任意模式 → 直接加载（无需模式检查）
```

### 加载步骤

1. 检测到触发词 → 使用 Read 工具读取对应指令文件
2. 提取「行为约束」→ 叠加到当前会话行为规则
3. 提取「上下文加载」→ 按需加载关联文件
4. 提取「产物规范」→ 确定输出路径和格式
5. 告知用户指令已激活 + 关键约束摘要

## 典型使用场景

### 场景 1：默认开发
```
用户："帮我加个导出功能"
→ TL 模式（默认），无 with 指令
→ TL 自行判断：设计 → 编码 → 完成
```

### 场景 2：目标澄清 + 计划先行

```
用户："/withGrill /withPlan 帮我澄清并规划对账模块"
→ TL 模式 + /withGrill + /withPlan
→ AI 从业务用户+系统设计双视角生成澄清问题 → 写入独立 grill 明细文件
→ 用户在 grill 文件中答疑 → grill 门禁通过
→ Agent 按结构化格式归集回目标总览
→ TL 设计方案 → 落盘计划 → 等待确认 → 编码
```

### 场景 2.5：目标理解 + 子目标拆解
```
用户："/withGo GOAL-102"
→ TL 模式 + /withGo
→ Agent 读取目标总览，理解 GOAL-102 目标效果和最近完成
→ 先判断用户真实意图和需求成熟度：线索 / 需求草稿 / 可计划需求 / 可执行小修
→ 将旧“当前分点”兼容整理为“当前子目标”
→ 只把确定信息最小充分补充到子目标；推断和缺口写入待确认
→ 判断业务口径、页面入口、接口契约、数据结构和验收边界是否足够清楚
→ 清楚则建议进入 /withPlan /withReview；不清楚则只输出待确认问题或建议 /withGrill
```

### 场景 2.6：对话需求归集

```
用户："/withRequirement 开票列表和明细都要支持导出，并为后续多明细合并导出预留接口"
→ TL 模式 + /withRequirement
→ Agent 先判断用户意图：只登记、需澄清，还是要求继续生成计划
→ 提取本期范围、后续预留和注意事项
→ 匹配已有 Goal、查重并登记为未完成子目标
→ 对清晰主题返回一行式新对话推进提示词；对关键口径不清主题返回澄清提示词
→ 不实施需求，不创建计划，不修改代码
```

### 场景 2.7：需求归集 + 计划落盘

```
用户："/withRequirement /withPlan 把这段需求分析后登记到目标总览，并生成实施计划"
→ TL 模式 + /withRequirement + /withPlan
→ Agent 提取需求，匹配既有 Goal，做最小充分登记
→ 若门禁结论为可推进：按 withPlan 和产物规范写入 ART-TL-实施计划.md，status=in_review
→ 若门禁结论为需澄清：不写计划，只输出待确认问题或 /withGrill 提示词
→ 无论是否生成计划，都不修改项目代码，等待用户确认
```

### 场景 3：计划先行
```
用户："/withPlan 帮我重构用户模块"
→ TL 模式 + /withPlan
→ TL 设计方案 → 落盘计划 → 等待确认 → 编码
```

### 场景 4：完整五件套（含目标澄清）
```
用户："/withGrill /withPlan /withReview /withTest /withMock 新增对账模块"
→ TL 模式 + 五个 with 指令叠加
→ AI 从双视角生成澄清问题 → 写入独立 grill 明细文件
→ 用户答疑 → grill 门禁通过 → Agent 归集回目标总览
→ TL 设计方案 → 落盘计划
→ 派发 subAgent 审核计划 → 审核报告 + 计划呈现用户
→ 用户确认 → TL 编码
→ 派发 subAgent 生成测试计划 → 审查
→ 派发 subAgent 生成测试数据 SQL → 审查
```

### 场景 5：框架改进
```
用户："/asTeacher 角色技能映射需要更新"
→ 教学模式
→ 框架顾问直接修改 → 报告
```

### 场景 6：IMPORTANT TODO 分析

```
用户："分析标记" 或 /withAnnotate
→ TL 模式 + /withAnnotate
→ Agent 扫描所有 /** IMPORTANT TODO */ → 逐个分析数据来源和处理步骤
→ 生成全流程注释（层级 2）
→ 穿透分析直接依赖方法（一层深度）→ 重要方法补全注释
→ 所有 /** IMPORTANT TODO */ → /** IMPORTANT */
→ 验证零残留 → 口头报告
```

### 场景 8：需求收件箱处理

```
用户："处理收件箱"
→ TL 模式 + /withInbox
→ Agent 扫描 _需求收件箱/ → 逐个分析需求文件夹
→ 搜索现有 GOAL 做去重和关联检查
→ 口头列出需求摘要 + 建议归属（新 GOAL / 追加到现有 GOAL）
→ 用户确认 → Agent 写入目标总览 → 需求文件夹移动到 _已处理/
→ 口头建议是否需要 /withGrill 对新分点做深度澄清
```

### 场景 9：需求导出

```
用户："/withOutbox GOAL-002 P5"
→ TL 模式 + /withOutbox
→ Agent 确认 Goal 和分点 → 扫描产物目录 → 筛选非代码文件
→ 去标识化：文件名/目录名/frontmatter/正文引用全部去 GOAL 编号
→ 生成 README.md → 放入 _需求收件箱/{业务主题名}/
→ 口头报告导出结果
```

### 场景 10：管理分析
```
用户："生成本周周报"
→ 任意模式均可
→ Agent 读取 MGMT-Report.md → 收集本周数据 → 输出报告到 A.目标体系/管理报告/
```

### 场景 11：工时汇总
```
用户："帮我汇总上半月完成的工时"
→ 任意模式均可
→ Agent 读取 MGMT-Estimate.md → 解析时间范围 → 汇总分点 → 输出报告
```
