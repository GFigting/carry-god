# 知识沉淀 — Agent 使用指引

## 何时读取本板块

- Agent 执行任务前需要参考已有的技术方案、最佳实践或规范时
- Agent 完成技术调研后需要归档调研报告时
- Agent 遇到故障后需要写入经验教训时
- Agent 发现可复用的技术方案，需要归档到技术文档时
- Agent 需要查找某个技术领域的已有知识时
- Agent 被要求按照某项编码规范或最佳实践执行时
- 人类要求 Agent 从外部资源收集信息并归档时

## 知识分类

### 最佳实践（`最佳实践/`）
- 命名格式：`BP-{主题}.md`，如 `BP-编码规范.md`
- 内容：经过团队验证和采纳的规范和约定
- 读取场景：Agent 执行编码、提交、API 设计、日志记录等操作时，应首先检查是否存在对应的最佳实践文档

### 技术文档（`技术文档/`）
- 按技术领域分子目录：前端、后端、数据库、基础设施、安全
- 内容：方案设计文档、API 文档、架构说明、部署手册
- 读取场景：Agent 需要在特定技术栈下工作时，查对应领域目录

### 经验教训（`经验教训/`）
- 内容：故障复盘报告、问题根因分析（RCA）、改进措施记录
- 读取场景：Agent 处理类似故障时应先查阅历史经验；故障处理完成后应在此归档

### 外部资源（`外部资源/`）
- 内容：有用的外部文档链接、博客文章、论文参考
- 读取场景：Agent 需要外部参考资料时

### 技术调研（`技术调研/`）
- 内容：技术对比分析、POC 验证报告、竞品分析结果
- 读取场景：Agent 进行技术选型前应先查看是否已有相关调研；调研完成后应在此归档

### 业务领域（`业务领域/`）
- 内容：与特定行业/业务线相关的知识，如财务结算规则、供应链流程、CRM 客户管理策略等
- 分类：按业务线或领域分子目录（如 `财务/`、`供应链/`、`客户管理/`、`合规/`）
- 读取场景：Agent 执行业务相关任务时，先查阅对应业务领域的知识；业务专家提供的规则和流程也应在此归档
- **与技术知识的区别**：技术知识讲"怎么做"（how），业务知识讲"做什么"（what）和"为什么"（why）。两者分开管理，避免技术文档被业务上下文淹没
- **命名规范**：`{业务主题}.md`，如 `财务-结算对账规则.md`

## 知识模板使用

创建知识文档时使用 `.obsidian/templates/tpl-knowledge.md` 模板。模板包含标准的 frontmatter 结构：

```yaml
---
type: knowledge
id: "KNOW-YYYY-NNN"            # 自动生成
title: "{标题}"
domain: "{frontend/backend/infrastructure/data/security/mobile/business/general}"
topic: "{主题关键词}"
maturity: draft                # draft / verified / adopted / deprecated
source: "{来源任务ID}"
author: "{创建者}"
related_roles: []              # 关联角色ID列表
related_work_types: []         # 关联工作类型ID列表
needs_review: false            # 是否需要人工审核
tags:
  - type/knowledge
  - domain/{领域}
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
---
```

**知识成熟度（maturity）**：
- `draft`：初稿，可能不完整或有待验证
- `verified`：已验证，经实践确认
- `adopted`：团队已采纳，成为标准做法
- `deprecated`：已过时，不再适用

## 何时创建知识文档的判断标准

Agent 在以下情况应创建知识文档：

1. **技术调研完成**：完成了技术选型、POC 验证或竞品分析 → 归档到 `技术调研/`
2. **故障处理完成**：完成了故障响应，有复盘价值 → 归档到 `经验教训/`
3. **可复用的技术方案**：产出了可被其他项目复用的方案设计 → 归档到 `技术文档/`
4. **发现新的最佳实践**：发现了跨项目通用的新规范或约定 → 归档到 `最佳实践/`
5. **收集到有价值的外部资源**：发现值得长期保留的外部参考 → 归档到 `外部资源/`
6. **项目级开发特殊要求**：某项目在开发中反复出现的模式、约定、规则 → 归档到 `技术文档/` 或 `最佳实践/`（详见下方「项目级开发约定归档流程」）

**不需要创建知识文档的情况**：
- 一次性的任务执行细节（任务文件本身就是记录）
- 简单的信息查询结果（直接回答即可）
- 与其他已有知识重复的内容（更新已有文档即可）

## 项目级开发约定归档流程

### 场景识别

当某个项目在开发过程中持续出现以下模式时，应触发知识归档：

| 信号 | 示例 | 归档时机 |
|------|------|----------|
| 结构相近的页面/组件反复出现 | FMS 的列表页、详情页、对账页结构高度相似 | 第 2-3 次遇到同类需求时 |
| 相同内容的处理方式被重复询问/查阅 | 权限配置方式、字典使用方式、日期格式化约定 | 首次被 TL 或 Agent 查阅时即可归档 |
| 项目特有的技术约束或依赖 | "FMS 对账必须通过中台 lsmd 表"、"芋道路由组件匹配规则" | 发现并确认后立即归档 |
| 项目级编码约定 | 某项目的 API 命名风格、包结构约定、错误码规范 | 团队达成共识后 |
| 权限/配置的收集整理 | 某项目特有的角色-权限映射、菜单配置规则 | 每次变更后更新已有知识 |

### 归档路径决策

```
发现项目级特殊要求/约定
    │
    ├── 是编码规范/约定类（"怎么写"）？
    │   └── → 最佳实践/BP-{项目缩写}-{主题}.md
    │       例：BP-fms-ui-前端开发规范.md
    │
    ├── 是技术架构/依赖/陷阱类（"怎么配/怎么避"）？
    │   ├── 通用技术知识 → 技术文档/KB-{主题}.md
    │   │   例：KB-Lombok-Builder与MapStruct继承陷阱.md
    │   └── 项目特定技术 → 技术文档/KB-{项目缩写}-{主题}.md
    │       例：KB-fms-rear-中台lsmd表依赖.md
    │
    ├── 是数据库/表结构相关？
    │   └── → 技术文档/数据库/{项目缩写}/
    │       例：技术文档/数据库/fms-rear/KB-fms-rear-字典测试数据SQL约定.md
    │
    ├── 是业务规则/流程（"做什么/为什么"）？
    │   └── → 业务领域/{业务线}/
    │       例：业务领域/财务/财务-结算对账规则.md
    │
    └── 不确定？
        └── → 默认放 技术文档/KB-{项目缩写}-{主题}.md，TL 审查后调整
```

### 与项目 docs/ 的分工

| 存放位置 | 内容性质 | 生命周期 | 受众 |
|---------|---------|---------|------|
| **框架知识库** `知识沉淀/` | AI Agent 执行任务时需要参考的开发约定、技术约束、踩坑记录 | 长期维护，随项目演进更新 maturity | Agent + 人类开发者 |
| **项目 docs/** | 项目的正式文档（README、架构说明、部署手册、业务文档） | 随项目代码版本一起演进 | 人类开发者 |
| **产物工件** `A.产物工件/TASK-YYYY-NNN/` | 某次任务的具体产出（方案设计、评审报告） | 任务完成后同步到项目 docs/ 或归档到知识库 | 任务相关方 |

> **核心区分**：框架知识库存的是"以后做类似任务时要知道的东西"（面向 Agent 的长期记忆），项目 docs 存的是"这个项目是什么"（面向人类的正式文档）。两者不互斥——一份内容可能在两边都需要，此时先在产物工件中迭代 → 任务完成后同步到项目 docs/，同时提炼可复用部分归档到知识库。

### 归档操作步骤

```
1. 识别到项目级特殊要求/约定
2. 按路径决策树确定归档位置
3. 检查目标目录是否存在，不存在则创建（如 `知识沉淀/最佳实践/`、`知识沉淀/技术文档/数据库/{项目缩写}/` 等）
4. 使用 tpl-knowledge 模板创建文档
5. Frontmatter 填写要点：
   - domain: 按内容选（backend/frontend/business/...）
   - source: 关联触发归档的任务 ID
   - maturity: draft（首次归档）
   - related_roles: 关联会用到此知识的角色
6. 核心内容必须包含：
   - 具体的代码示例（正例 ✅ + 反例 ❌）
   - 适用边界（什么时候用、什么时候不用）
   - 已知的坑和注意事项
7. 在任务文件中记录归档操作
8. 后续遇到相同场景时，Agent 应先查阅知识库再执行
```

### 知识归档决策矩阵

Agent 在任务完成后，按以下矩阵自动判断是否需要归档以及归档位置：

| 任务类型 (work_type) | 产出类型 | 归档位置 | 触发条件 |
|----------------------|----------|----------|----------|
| WT-新功能开发 | 技术方案/架构设计 | `技术文档/{领域}/` | 方案有复用价值，非一次性 |
| WT-新功能开发 | 编码规范/约定沉淀 | `最佳实践/` | 经团队评审确认，非个人偏好 |
| WT-Bug修复 | 故障根因分析 | `经验教训/` | P0/P1 级别，有复盘价值 |
| WT-技术调研 | 调研报告/POC结果 | `技术调研/` | 每次调研完成均归档 |
| WT-技术调研 | 外部参考链接 | `外部资源/` | 发现有价值的长期参考 |
| WT-性能优化 | 优化方案与数据 | `技术文档/{领域}/` | 有可量化的优化结果 |
| WT-故障响应 | 故障复盘报告 | `经验教训/` | 每次故障处理完成 |
| WT-迭代计划 | 迭代总结 | `经验教训/` | 含可改进的经验 |
| WT-代码重构 | 重构模式/设计 | `最佳实践/` | 产出可复用的设计模式 |
| WT-信息收集 | 收集到的信息 | `外部资源/` 或 `技术调研/` | 按 PROC-AUTO-001 流程 |
| WT-新功能开发 | 业务规则/流程 | `业务领域/{业务线}/` | 涉及业务逻辑，有长期参考价值 |
| WT-业务分析 | 行业知识/业务规则 | `业务领域/{业务线}/` | 业务专家提供的规则和流程 |

**归档决策流程**：
```
任务完成 → 检查产出类型 → 查决策矩阵 → 匹配归档位置?
  ├── 是 → 使用 tpl-knowledge 模板创建文档 → 关联任务ID → 更新知识库索引
  └── 否 → 跳过归档，仅完成任务文件
```

**自动归档信号**：Agent 在任务文件中设置 `needs_knowledge_archive: true` + `archive_path: "{路径}"` 即触发归档流程。

## 通识级收件箱处理协议（未整理信息 → 结构化知识）

### 设计理念

人类不可能保证遇到的所有新知识都是 `.md` 格式。链接、截图、聊天记录、随手粘贴的文本——都应有入口存放。本协议定义"人类触发 + Agent 辅助"（B 方案）的收件箱模式。

### 收件箱路径

Agent 从 `配置与元数据/框架设置.yaml` 读取 `knowledge.inbox` 字段。若为空，默认使用 `知识沉淀/未处理信息/`。

### 人类操作

1. 遇到任何有价值但未结构化的信息 → 扔进收件箱
2. 格式不限：`.md`、`.txt`、`.png`（截图）、`.url`（链接快捷方式）、纯文本粘贴均可
3. 文件名建议包含主题关键词，但不强制（`未命名.md` 也可接受）
4. 想整理时说一句"整理一下收件箱"或"处理未处理信息"

### Agent 处理流程

```
人类触发："整理收件箱" / "处理未处理信息"
          ↓
Agent 读取收件箱目录 → 逐个文件分析内容
          ↓
按主题聚类（同一主题的多条信息合并为一条知识）
          ↓
对每条聚类结果，走 知识归档决策矩阵（见上文）→ 确定归档位置
          ↓
使用 tpl-knowledge 模板创建结构化文档 → 写入知识库根路径
          ↓
原始信息移动到 _已处理/（保留追溯，不直接删除）
          ↓
口头报告：处理了哪些、产出了哪些知识文档
```

### Agent 行为约束

- **去重**：归档前检查知识库是否已有同类知识，有则更新而非新建
- **保留来源**：归档文档的 `source` 字段注明原始信息文件名
- **不确定时标记**：无法确定分类的信息，归档到 `技术文档/` 并标记 `maturity: draft` + `needs_review: true`
- **不删除原始信息**：处理完移动到 `_已处理/`，人类确认后可手动清理

### 收件箱目录结构

```
{inbox_path}/
├── README.md              ← Agent 创建：收件箱使用说明（人类可见）
├── 一篇随手贴的文章.txt
├── 2026-06-17-故障截图.png
└── ...
```

## 与其他板块的联动

- **任务系统**：任务完成后如有知识产出，应在知识沉淀中归档。任务文件中可添加链接指向归档的知识文档。
- **工作体系**：工作类型定义中的 context_pack 可能引用知识沉淀中的最佳实践和技术文档作为 optional 上下文。
- **流程引擎**：流程的某些节点可能要求在特定知识文档指导下执行（如编码节点参考 BP-编码规范）。
- **角色体系**：角色定义中的 skills 和 tools 字段可能与知识沉淀中的技术文档关联。
- **导航系统**：`导航系统/📑_知识索引.md` 提供了按领域浏览知识文档的入口。
- **日志与追踪**：日报/周报中可能引用知识沉淀中的关键发现或经验教训。
- **配置与元数据**：知识文档必须使用 `type/knowledge` 和 `domain/{领域}` 标签。

## Agent 操作清单

1. **查知识**：执行任务前，先查 `📚_知识库总览.md` 确定是否有相关领域的已有知识
2. **读规范**：编码前读 `BP-编码规范.md`，提交前读 `BP-Git工作流.md`，设计 API 前读 `BP-API设计规范.md`
3. **阅历史**：处理故障前，先查 `经验教训/` 看是否有类似历史案例
4. **创建知识文档**：满足创建条件时，使用 `tpl-knowledge` 模板创建新文档：
   - 选择正确的分类目录
   - 填写完整的 frontmatter（type、domain、topic、maturity、tags）
