# 代码审查检查清单

本检查清单用于 [[PROC-代码审查流程]] 的 `node_human_review` 节点，指导代码审核员从逻辑正确性、安全性、性能、可维护性和测试覆盖五个维度系统性审查 Pull Request。

## 检查项

| # | 检查项 | 通过标准 | 不通过处理 |
|---|--------|---------|-----------|
| 1 | 逻辑正确性——核心业务逻辑 | 业务逻辑实现与技术方案/需求文档一致，正常路径、边界条件和异常路径均已正确处理 | 标注为 Block 级问题，指明具体文件、行号、逻辑缺陷描述，要求开发修正后重新提交审查 |
| 2 | 逻辑正确性——边界条件和异常处理 | 空值/null 输入已处理、数组越界已防护、数值溢出已考虑、外部依赖调用失败有降级或兜底逻辑 | 标注为 Block 级问题，提供具体边界场景和预期处理方式 |
| 3 | 安全性——注入防护 | 无 SQL 注入（使用参数化查询/ORM）、无 XSS（输出编码）、无命令注入、无路径遍历风险 | 标注为 Block 级问题，任何安全漏洞必须修复后方可合并 |
| 4 | 安全性——权限与认证 | 敏感接口有权限校验、用户输入做了服务端验证（不依赖前端校验）、无越权访问风险（水平/垂直越权） | 标注为 Block 级问题，指明缺少权限控制的具体接口或方法 |
| 5 | 性能——数据库与 IO 操作 | 无 N+1 查询、大数据量查询有分页/索引、批量操作已使用批处理、避免循环内数据库调用 | 标注为 Block 级问题（可预见的性能瓶颈影响用户体验），给出优化方案建议 |
| 6 | 性能——资源管理 | 数据库连接正确释放、文件流/网络连接在 finally 或 try-with-resources 中关闭、无内存泄漏风险（如集合缓存无限增长） | 标注为 Block 级问题，指出资源泄漏的具体位置和修复方式 |
| 7 | 可维护性——代码结构与命名 | 函数长度合理（建议 <= 40 行）、类和模块职责单一、命名清晰表意（避免 a/b/c/temp 等无意义命名） | 标注为 Comment 级问题（建议优化），严重结构混乱（如千行函数、上帝类）升级为 Block |
| 8 | 可维护性——注释与文档 | 复杂算法有注释说明意图、公开 API 有文档注释（JSDoc/JavaDoc 等）、魔法数字已替换为命名常量 | 缺失关键注释按 Comment 处理；如为公开 API 缺失文档则按 Block 处理 |
| 9 | 测试覆盖——单元测试 | 新增/变更代码有对应的单元测试，测试覆盖主要分支和边界条件，Mock/Stub 使用合理 | 无测试标注为 Block 级问题；测试质量不足（仅覆盖 happy path）标注为 Request Changes |
| 10 | 测试覆盖——集成影响 | 变更涉及外部接口调用（数据库 Schema、API 契约、消息格式）时，集成测试已覆盖且通过 | 缺少集成测试标注为 Block 级问题，须补充并通过后方可合并 |
| 11 | 代码风格——格式规范 | 代码通过自动格式化工具（ESLint/Prettier/Checkstyle），缩进、命名约定、文件组织符合团队规范 | CI 自动检查已覆盖该维度，人工审查阶段仅做抽查；人工发现的风格问题按 Comment 处理 |

## Agent 使用说明

当 Agent 以 [[ROLE-QA-002]] 角色执行本检查清单时：

1. **审查准备**：读取 PR 的完整 diff、关联的需求文档和技术方案文档，了解变更意图和范围
2. **逐项审查**：按检查项顺序逐维度分析代码，每个检查项需同时审查所有变更文件
3. **问题分级**：每个发现的问题必须标注级别——
   - **Block**：必须修改，否则不可合并（安全漏洞、逻辑错误、严重性能问题、无测试）
   - **Request Changes**：建议修改，审核员强烈建议但可协商（可维护性差、测试覆盖不足）
   - **Comment**：优化建议，不阻塞合并（代码风格、命名建议、可选优化）
4. **问题记录格式**：每条问题输出为 `文件路径:行号 | 级别 | 检查项# | 问题描述 | 修改建议`
5. **输出审查意见列表**：将所有发现的问题按类别组织，生成结构化的审查意见列表
6. **最终结论**：综合所有检查项给出审查结论——Approve（无 Block 级问题）/ Request Changes（存在 Block 级问题）/ Comment（仅有 Comment 级问题）
7. **紧急修复场景**：若审查对象来自 [[PROC-紧急修复流程]]，仅检查检查项 1-4（正确性+安全性），跳过性能、可维护性和代码风格检查项，并在结论中标注"简化审查"

### 输入文件获取指引

- **PR diff**：通过 Git 平台 API 或 `git diff` 命令获取
- **需求文档**：位于 `3.任务系统/` 目录，以任务 Ticket ID 关联
- **技术方案**：位于 `5.知识沉淀/技术方案/` 目录
- **编码规范**：位于 `5.知识沉淀/最佳实践/BP-编码规范.md`
