# 安全审查检查清单

本检查清单用于 [[PROC-需求到上线]] 和 [[PROC-发布流程]] 中的安全审查环节，确保系统在认证授权、数据保护、注入防护和依赖安全等方面满足安全基线要求。建议在每个迭代末或发布前执行完整检查。

## 检查项

| # | 检查项 | 通过标准 | 不通过处理 |
|---|--------|---------|-----------|
| 1 | 认证机制——会话管理 | 会话 Token 使用安全随机生成、有效期合理（建议不超过 24 小时）、支持主动失效（登出/密码变更后旧 Token 失效）、Cookie 设置 HttpOnly + Secure + SameSite | 修复不符合项，短效 Token 策略可协商；记录风险并设定修复截止日期 |
| 2 | 认证机制——凭证安全 | 密码使用强哈希算法存储（bcrypt/argon2）、无明文密码出现在日志或错误消息中、登录失败有限速/锁定机制、MFA 已启用 | 密码哈希算法不达标必须立即修复（Block）；限速机制缺失按高危处理 |
| 3 | 授权控制——访问控制 | 每个 API 端点有明确的权限校验（非仅前端路由拦截）、无水平越权（用户 A 可访问用户 B 数据）、无垂直越权（普通用户可执行管理员操作） | 标注为 Block 级问题，必须在使用权限校验的中间件/装饰器中补齐权限控制 |
| 4 | 数据保护——敏感数据存储 | 密码/密钥/Token 等敏感数据在数据库中加密存储或哈希存储、配置文件中的密钥使用环境变量或密钥管理服务（非硬编码）、备份数据同等加密 | 发现硬编码密钥/密码立即清除并轮换；未加密存储设定修复期限（不超过 1 个迭代） |
| 5 | 数据保护——传输加密 | 所有 API 通信强制使用 HTTPS/TLS 1.2+、内部服务间通信使用 mTLS 或等效加密、证书在有效期内且未使用自签名证书 | 禁用 HTTP 明文字段，配置 HSTS 头；证书即将过期须更新 |
| 6 | 注入防护——输入验证 | 所有用户输入有服务端白名单校验（类型、长度、格式、范围）、SQL 查询使用参数化/预编译（禁止字符串拼接）、动态命令执行（exec/system）已消除或严格沙箱化 | 任何注入防护缺失标注为 Block 级问题；输入校验缺失按高危修复 |
| 7 | 注入防护——输出编码 | HTML 输出上下文使用正确的编码函数（HTML entity / JS encode / URL encode）、API 响应 Content-Type 头正确设置（防 MIME 嗅探）、CSP 头已配置 | 输出编码缺失标注为 Block；CSP 配置为建议优化级 |
| 8 | 依赖安全——第三方库 | `npm audit` / `pip audit` / OWASP Dependency Check 无 Critical/High 漏洞、依赖版本在维护期（非 EOL 版本）、SBOM 可获取 | 升级存在已知漏洞的依赖至安全版本；无法升级的需补充缓解方案和风险评估 |
| 9 | 依赖安全——基础镜像 | 容器基础镜像使用官方/可信源、镜像已扫描无高危漏洞、镜像以非 root 用户运行、使用特定版本 Tag（非 latest） | 更换为基础镜像官方安全版本，配置非 root 运行，修复后重新构建 |
| 10 | 日志与审计——安全事件记录 | 认证事件（登录/登出/失败）记录到日志、权限拒绝事件记录、敏感操作（删除/导出/权限变更）有审计日志、日志不含敏感信息（密码/Token/PII） | 缺失关键审计日志标注为 Block；日志含敏感信息须立即脱敏 |
| 11 | CSRF 与 SSRF 防护 | 状态变更请求（POST/PUT/DELETE）使用 CSRF Token 或 SameSite Cookie、服务端发起的 HTTP 请求对目标 URL 做白名单校验（防 SSRF） | CSRF 防护缺失按高危修复；SSRF 白名单缺失标注为 Block |
| 12 | 安全头配置 | 响应包含安全 HTTP 头：CSP、X-Content-Type-Options: nosniff、X-Frame-Options: DENY、Strict-Transport-Security、Referrer-Policy | 缺失关键安全头按需补齐；HSTS 缺失标注为高危 |

## Agent 使用说明

当 Agent 以 [[ROLE-QA-002]] 或 [[ROLE-ARCH-001]] 角色执行本检查清单时：

1. **审查范围确认**：确认本次审查的范围（全量审查 / 增量审查），增量审查聚焦本次变更涉及的 API 端点、数据库操作、配置变更和新增依赖
2. **自动化扫描先行**：先运行自动化安全扫描工具（如 npm audit、Trivy、OWASP ZAP、SonarQube），将扫描结果作为人工审查的输入
3. **逐项证据采集**：每项检查需从具体来源获取证据——
   - 检查项 1-3：从认证中间件代码、路由权限配置、API 定义文件中检查
   - 检查项 4-5：从配置文件、环境变量管理、证书管理工具中检查
   - 检查项 6-7：从代码中搜索 SQL 拼接模式、HTML 渲染逻辑、HTTP 响应头配置
   - 检查项 8-9：运行 `npm audit` / `pip audit` 等依赖扫描工具
   - 检查项 10-11：检查日志记录代码、HTTP 客户端调用代码
   - 检查项 12：使用 curl 或浏览器 DevTools 检查实际响应头
4. **问题分级**：每个发现的问题标注严重级别——
   - **Block（阻塞）**：可导致数据泄露、权限绕过、系统被入侵的安全漏洞，必须修复后上线
   - **High（高危）**：存在被利用可能但利用条件较高的漏洞，建议在本次发布前修复
   - **Medium（中危）**：安全最佳实践偏离，建议在下一迭代修复
   - **Low（低危）**：优化建议，不设期限
5. **输出安全审查报告**：汇总所有检查项结果，含「检查项# | 结果 | 严重级别 | 发现描述 | 修复建议 | 修复截止日期」
6. **依赖漏洞处理**：对于依赖扫描发现的漏洞，需评估是否在代码中实际使用到受影响的功能（可达性分析），不可达的漏洞可降级处理
7. **人类介入点**：检查项中涉及架构级安全决策（如认证方案选型、加密算法选择）需人类架构师确认
