# 项目代码质量自检清单

本检查清单用于 `/withFinish` 流程中的代码质量自检步骤，由 **TL 或 代码质量检查员 (ROLE-QA-004)** 执行。聚焦项目编码规范，不涉及架构审查和业务逻辑审查。

## 核心原则

- **只对规范，不对逻辑**：检查代码是否符合项目约定写法，不判断业务是否正确
- **规则来源在项目 docs/**：具体约定以项目 `docs/` 中的文档为准，本清单提供维度框架
- **通过/不通过二值输出**：不评级别，只报告问题位置 + 违规项 + 修复建议

---

## 检查维度

### 1. Mapper / Repository 数据访问性能与规范

> **此维度关注数据库交互的性能和安全性**。循环内数据访问（N+1 查询 / 逐条更新）是业务代码中最常见的性能杀手，对大数据量场景影响极大，是检查重点。

| # | 检查项 | 通过标准 | 规则来源 |
|---|--------|---------|---------|
| 1.1 | 批量查询工具使用 | 多 ID 查询场景使用了 `selectList(in(...))` 或等价批处理方法，避免循环内逐条查询 | 项目 `docs/util-batch-query-conventions.md`（如有） |
| 1.2 | 列表查询条件拼装 | 文本搜索字段使用 `likeIfPresent`，编码/状态字段使用 `eqIfPresent`，语义正确 | `docs/util-list-query-conventions.md` |
| 1.3 | 无循环内数据库访问 | for/forEach 循环内无 `selectById`/`selectList`/`updateById`/`save`/`insert` 等单条数据库调用。批量操作应先收集 ID，循环外一次完成 | 目视 ServiceImpl 方法体 |
| 1.4 | 分页/导出查询一致性 | 分页查询和导出查询共用同一套条件拼装逻辑，避免两套口径漂移 | 对比 PageReqVO 和 ExportReqVO 对应的 Mapper 方法 |
| 1.5 | 更新字段最小化 | 更新操作不使用 `updateById(完整DO)` 来更新单列或少数列——会生成全字段 SET 子句，造成**并发覆盖风险** + **写放大**。应使用 `update(entity, LambdaUpdateWrapper)`：entity 仅设变更字段，MyBatis-Plus NOT_NULL 策略只生成变更列 + update_time | 目视 ServiceImpl 更新方法 |

### 2. 常量管理

| # | 检查项 | 通过标准 | 规则来源 |
|---|--------|---------|---------|
| 2.1 | 无魔法数字/字符串 | 业务语义的数字和字符串已提取为命名常量 | 项目 `constant/` 包 |
| 2.2 | 常量类位置规范 | 常量定义在项目约定的常量包中（如 `constant/` 或 `enums/`），不散落在业务代码中 | 项目 README 包结构说明 |
| 2.3 | 常量注释清晰 | 每个常量有注释说明其业务含义，非自解释的常量有额外说明 | 目视检查 |

### 3. 异常处理

| # | 检查项 | 通过标准 | 规则来源 |
|---|--------|---------|---------|
| 3.1 | 业务异常标准写法 | 业务校验失败使用 `ServiceExceptionUtil.exception(ERROR_CODE, params...)`，不抛裸 `RuntimeException` / `IllegalArgumentException` / `IllegalStateException` | `docs/tech-error-handling.md` |
| 3.2 | 错误码维护 | 新增错误码已注册在 `ErrorCodeConstants.java` 对应分段中，编码格式符合项目规范 | `docs/tech-error-handling.md` |
| 3.3 | 错误信息可用 | 错误码的 `msg` 模板使用 `{}` 占位符携带动态参数，用户可理解错误原因 | `docs/tech-error-handling.md` |

### 4. 字典维护

| # | 检查项 | 通过标准 | 规则来源 |
|---|--------|---------|---------|
| 4.1 | 字典 SQL 幂等 | 字典数据 INSERT 使用 `WHERE NOT EXISTS` 或等价幂等写法，非 `DELETE + INSERT` | `docs/skills/dict-template/SKILL.md` |
| 4.2 | 枚举→字典映射正确 | 枚举的 `code`/`value`/`type` 字段优先作为字典 `value`，`label` 取自 `name`/`desc` 等描述字段 | `docs/skills/dict-template/SKILL.md` |
| 4.3 | dict_type 命名规范 | `dict_type` 按项目已有约定蛇形命名，不随意创造新前缀 | 参考项目现有 `DictTypeConstants` |
| 4.4 | 字典常量注册 | 新增 `dict_type` 已在 `DictTypeConstants` 中注册常量 | 目视检查 |

### 5. 导入/导出/上传等特殊功能

> **此维度聚焦文件 I/O 相关功能**——这些代码通常不涉及复杂业务逻辑，但容易因框架/工具的隐性约定而翻车。检查者无需理解业务，只对照规则做模式匹配。

| # | 检查项 | 通过标准 | 规则来源 |
|---|--------|---------|---------|
| 5.1 | EasyExcel 导入 VO 无链式 setter | 导入 VO 显式标注 `@Accessors(chain = false)` 或类未启用链式 setter（无全局 `lombok.accessors.chain=true` 或已有 `@Accessors(chain = false)`）。若项目有全局 chain 配置且导入 VO 未覆盖，字段将全为 null | `知识沉淀/技术文档/后端/KB-Lombok-chain与EasyExcel导入陷阱.md` |
| 5.2 | 导入资源关闭 | `InputStream` 在使用后正确关闭（try-with-resources 或 finally 块），`MultipartFile` 的流未在方法外泄露 | 目视检查 |
| 5.3 | 导出 VO 列匹配 | 导出 VO 的 `@ExcelProperty` 列名与业务含义一致，列顺序符合人类预期。导出字段是 VO 字段的超集而非子集（避免遗漏列） | 对比 ExportReqVO 与 ExcelVO |
| 5.4 | 导出大数据量风险 | 导出未使用 `doReadAllSync()`/全量加载（对有大数据量的表）；导出的 `selectList` 方法未加 limit 保护 | 目视 ServiceImpl 导出方法 |
| 5.5 | 上传文件校验 | 上传接口有文件类型/大小校验（前端+后端双重），未直接信任文件名扩展名 | 目视 Controller 上传方法 |
| 5.6 | 文件路径安全 | 文件读写路径通过配置获取或使用框架工具方法拼接，未拼接用户输入直接作为路径（路径穿越风险） | 目视文件读写代码 |

### 6. 代码注释与可审核性

> **此维度关注代码的可读性和人工审核效率**。业务逻辑正确性必须由人工审核，AI 的职责是通过注释让审核者无需追踪调用链即可理解代码全貌。检查者不判断注释的业务准确性，只检查注释的存在性和格式完整性。

| #   | 检查项                 | 通过标准                                                                                                               | 规则来源                        |
| --- | ------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| 6.1 | 公共接口 JavaDoc 完整     | Controller/@FeignClient/Service 接口的所有 public 方法有完整 JavaDoc（方法作用描述 + @param 逐一说明 + @return 含义说明），void 方法可省略 @return | `通用能力层/工具手册/UTIL-代码注释规范.md` |
| 6.2 | 重要方法全流程注释           | 满足"重要方法判定规则"（R1-R8）的新增/修改方法有全流程注释（`<p>整体逻辑说明：` + 编号步骤列表，每步含数据来源和处理动作）                                              | `通用能力层/工具手册/UTIL-代码注释规范.md` |
| 6.3 | IMPORTANT 标记一致      | 标记了 `/** IMPORTANT */` 的方法必须同时有全流程注释（层级 2）；有全流程注释的重要方法应有 `/** IMPORTANT */` 标记（双向一致性）                              | `通用能力层/工具手册/UTIL-代码注释规范.md` |
| 6.4 | 无 IMPORTANT TODO 残留 | 代码中不存在 `/** IMPORTANT TODO */` 标记。如有残留，在报告中提示"建议使用 `/withAnnotate` 分析"                                             | `通用能力层/工具手册/UTIL-代码注释规范.md` |

**注意**：维度 6 仅检查**本次新增或修改**的代码行，不对存量代码全量补扫描。若某存量方法没有全流程注释但本次未被修改，不视为违规。

### 7. 数据结构字段分组与可审核性

> **此维度关注表结构和数据库模型的人工可读性**。检查者不判断字段业务口径是否正确，只检查 SQL/DO/数据库交互 VO 是否按字段职责组织，避免复杂表字段无序堆叠。

| #   | 检查项           | 通过标准                                                                                                                       | 规则来源                             |
| --- | ------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 7.1 | DDL 字段分组注释    | 新建/重构复杂业务表 DDL 使用注释块区分关联字段、业务字段、基础展示字段、系统管理字段；复杂业务字段按金额、状态、开票收款等职责继续细分                                                     | `通用能力层/工具手册/UTIL-SQL管理规范.md`     |
| 7.2 | 字段顺序合理        | 新增字段放在同类字段附近；若受工具限制只能追加，SQL 或代码注释说明目标分组；系统管理字段不夹杂在核心业务字段中                                                                  | 目视 SQL / DO                      |
| 7.3 | DO 字段分组一致     | DO / Entity / DataObject 与表结构直接对应时，字段顺序与 SQL 分组基本一致，并使用短注释分隔字段群                                                            | 目视 DO                            |
| 7.4 | 数据库交互 VO 分组   | 直接承载 Mapper 查询结果、数据库层投影、导入导出明细的 VO/DTO 按字段职责分组；普通前端请求 VO 不强制                                                               | 目视 VO/DTO                        |
| 7.5 | 可被引用明细 ID 稳定性 | 对可能被后续表引用的业务明细、分摊明细、流程明细，修改展示字段、分组字段或派生汇总时不得删除重插导致主键变化；应优先原行更新，必要时仅重建派生汇总行并回写明细归属。若确认为纯临时派生表，需在代码注释或设计文档中明确“ID 不稳定、禁止外部引用” | 目视 ServiceImpl / Mapper / SQL 设计 |

**注意**：维度 7 只检查本次新增或修改的 SQL/DO/数据库交互 VO，以及本次触碰的数据重建/重算逻辑。对存量大表不要求一次性重排；但本次新增字段不得继续扩大无序堆叠。

## Agent 使用说明

当 Agent 以 **ROLE-QA-004 代码质量检查员** 角色执行本检查清单时：

### 输入

TL 在派发时提供：
- **改动文件列表**：本次变更涉及的所有文件路径
- **改动意图描述**：简要说明本次变更的业务目的

### 执行流程

1. **加载规则来源**：根据项目读取 `docs/` 中的相关规范文件
2. **逐文件检查**：对每个改动文件，按八个维度逐项对照
3. **判定**：
   - 通过 → 该维度标记为 `[x]`
   - 不通过 → 记录 `文件:行号 | 维度# | 违规描述 | 修复建议`
4. **输出报告**：写入产物工件目录

# 代码质量检查报告

- 检查时间：YYYY-MM-DD HH:MM
- 改动范围：{文件数量} 个文件
- 检查结论：通过 / 不通过

## 逐维度结果

### 注意事项

- 若项目缺少某维度的规范文档，该维度标记为「跳过 — 项目未定义规范」，不视为不通过
- 对于 `_封存/` 目录或框架自身的改动，默认不执行此检查（非项目代码）
- 仅检查本次 **新增或修改** 的代码行，不对存量代码全量扫描
