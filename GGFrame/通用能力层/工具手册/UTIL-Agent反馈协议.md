# UTIL-Agent 反馈协议

## 目的

让 Agent 在 TL 模式执行任务过程中发现框架问题时，能以**极低成本**记录反馈到相关框架文件底部，供 Teacher 模式消费和改进。

**设计哲学**：人类判断"这是问题"，Agent 执行记录。反馈靠近问题出处（而非独立文件），Teacher 打开框架文件时自然看到。

## 核心原则

1. **人类触发，Agent 记录** — Agent 不自动创建反馈，除非人明确触发
2. **反馈内嵌框架文件** — 写在问题相关的框架文件底部 `## Agent 反馈` 区，而非独立文件
3. **格式极简** — 一行一条，人一眼能判断，无需重读对话上下文
4. **Teacher 消费后清理** — 处理后勾选或删除，保持框架文件整洁

## 触发方式

### 方式一：人主动喊停（TL 模式）

| 触发词 | 场景 |
|--------|------|
| `记下这个问题`、`反馈一下`、`记录这个问题`、`agent反馈` | 人对 agent 的产出/理解不满意，希望记录到框架 |

**Agent 行为**：
1. 识别问题最相关的框架文件（角色定义/模式指令/检查清单/工作类型等）
2. 在该文件底部追加一条反馈（若尚无 `## Agent 反馈` 区则先创建）
3. 口头确认：「已记录到 `{文件路径}`」

### 方式二：/withFinish 末尾询问

`/withFinish` 完成归一化最后一步（口头总结）中，Agent 主动询问：
> 本次是否有框架改进反馈需要记录？

如有，按同样方式追加到相关框架文件。

---

## 反馈格式

```markdown
## Agent 反馈

> 以下为 Agent 在工作过程中记录的框架改进线索。Teacher 处理后请勾选或删除。

- [ ] YYYY-MM-DD | {来源} — {问题简述}。建议：{改动方向}
```

### 格式约束

| 字段 | 说明 | 示例 |
|------|------|------|
| 日期 | 反馈产生日期 | `2026-06-24` |
| 来源 | Goal 编号或对话上下文 | `GOAL101`、`TL`、`asTeacher dream 讨论` |
| 问题简述 | 一句话说清问题，让 Teacher 无需重读对话 | `WITH-Finish.md 步骤2 未说明检查维度` |
| 建议 | 改动的具体方向（可选，Agent 不确定时可省略） | `补充 Mapper/常量/异常/字典 四维度` |

### 正例

```markdown
- [ ] 2026-06-24 | GOAL101 | TL — WITH-Finish.md 步骤2 只说"派发代码质量检查"但未说明检查什么维度，Agent 反复确认浪费 2 轮对话。建议：直接列出 Mapper/常量/异常/字典 四维度
```

### 反例（太啰嗦）

```markdown
- [ ] 2026-06-24 下午，我在执行 GOAL-101 的完成归一化流程时，发现 WITH-Finish.md 这个文件的第 48 行写的步骤 2 "代码质量检查"描述不够详细...（以下省略 200 字）
```

## 识别目标文件的指南

Agent 追加反馈时，需要判断问题与哪个框架文件最相关：

| 问题类型 | 目标文件（示例） |
|---------|---------------|
| 角色定义不清晰、权限矛盾 | `角色体系/ROLE-*.md` |
| 模式指令行为不当、约束缺失 | `角色体系/模式指令/as系列/AS-*.md` 或 `with系列/WITH-*.md` |
| 检查清单不完整 | `通用能力层/检查清单/CHK-*.md` |
| 工作类型输入输出不明确 | `_封存/工作体系/WT-*.md` |
| 流程编排问题 | `_封存/流程引擎/PROC-*.md` |
| 产物工件规范矛盾 | `配置与元数据/产物工件规范.md` |
| 根 CLAUDE.md 速查不准确 | `CLAUDE.md` |
| 跨文件矛盾 | 追加到**矛盾双方**中更基础的那一份（如角色 vs 指令 → 优先追加到指令） |
| 无法确定目标文件 | 追加到 `A.Teacher分析/agent反馈-未归类.md`（兜底） |

**原则**：优先追加到问题**根因**所在的文件，而非问题**表现**所在的文件。不确定时选更基础/更常被引用的那份。

## Teacher 消费流程

Teacher 模式激活时，或在浏览框架文件时：

```
发现文件底部有 ## Agent 反馈 区且含未勾选条目
    ↓
逐条阅读 → 评估是否构成有效的框架改进
    ↓
┌─ 有效 → 修改框架 → 勾选 `[x]` 或删除该条目
└─ 无效/不采纳 → 删除该条目（可口头向用户说明原因）
    ↓
所有条目处理完毕 → 可选：删除整个 ## Agent 反馈 区（保持文件整洁）
```

Teacher **不需要**主动扫描所有文件查找反馈——在正常浏览和修改框架文件时自然会遇到。

---

## 边界说明

| 场景 | 行为 |
|------|------|
| 反馈涉及多个文件 | 在**根因文件**追加一条，不在多个文件重复 |
| 同一个文件已有反馈区 | 在现有反馈区末尾追加，不创建新的 |
| 反馈内容与人理解一致 | 直接记录，无需人二次确认 |
| 反馈内容 Agent 不确定 | 口头向人确认后再记录 |
| Teacher 模式下触发 | 不适用——Teacher 本身可以直接改框架 |

---

## 与其他机制的交互

- **+ `/withFinish`**：完成归一化末尾询问是否有反馈
- **+ `/asTeacher`**：Teacher 浏览文件时自然消费反馈
- **+ `dream`**：dream 讨论中产生的改进想法 → 人直接更新 `梦想改造方案.md`，不用反馈协议（反馈协议是 TL 模式下的"轻量管道"）
