# 代码注释规范

## 概述

本规范定义 AI Agent（TL）在编码过程中必须遵循的注释标准。核心目标：**让人类审核者无需追踪代码调用链即可理解业务逻辑全貌**。

本规范与 `/withCheck` 的维度 6「代码注释与可审核性」配套使用——维度 6 检查注释**是否存在**，本规范定义注释**怎么写**。

---

## 注释层级

### 层级 1：标准 JavaDoc（所有公共接口必须）

**适用对象**：Controller / @FeignClient / Service 接口的所有 public 方法。

```java
/**
 * {方法作用的一句话描述}
 *
 * @param {paramName} {参数说明}
 * @return {返回值说明}
 */
```

**规则**：
- 一句话描述必须说清楚"这个方法做什么"，不能只是"xxx处理"或"xxx方法"
- @param 对每个参数逐一说明（基本类型可合并，如 `@param id 和 name`）
- @return 必须说明返回值含义，不能只写"返回值"或"结果"
- void 方法省略 @return

### 层级 2：全流程注释（重要方法必须）

**适用对象**：满足"重要方法判定规则"（R1-R8）的方法。在层级 1 基础上增加逻辑说明。

```java
/**
 * {方法作用的一句话描述}
 * <p>
 * 整体逻辑说明：
 * 1. {数据来源} — {处理步骤}
 * 2. {数据来源} — {处理步骤}
 * 3. {数据来源} — {处理步骤}
 *
 * @param {paramName} {参数说明}
 * @return {返回值说明}
 */
```

**规则**：
- `<p>` 分隔一句话描述和逻辑说明
- "整体逻辑说明："后跟编号列表，每一步说明**数据从哪里来 + 做了什么处理**
- 编号列表的每一步是一个完整的业务动作，不是代码行级别的逐行翻译
- 步骤数通常为 3-8 步，过多时考虑合并同类步骤
- 示例（来自实际业务）：

```java
/**
 * 同步OMS订单数据（支持日期范围或天数）
 * <p>
 * 整体逻辑说明：
 * 1. 从 OMS 数据源查询待同步的订单数据
 * 2. 分批处理订单主表数据（每批2000条）
 * 3. 同步发货地址信息
 * 4. 同步收货地址信息
 *
 * @param syncReqVO 同步请求参数（可指定日期范围或同步最近N天）
 * @return 同步结果（成功条数、失败条数）
 */
```

### 层级 3：类/组件级注释

**适用对象**：新增的 Service / Controller / 组件类。

```java
/**
 * {类/组件的定位说明——这个类在整个模块中扮演什么角色}
 * <p>
 * 重要功能：
 * - {功能1：做什么}
 * - {功能2：做什么}
 * - {功能3：做什么}
 *
 * @author {author}
 */
```

**规则**：
- 已有类不强制补全类级注释（只对新增类要求）
- "重要功能"列出 3-5 项主要公共方法及其作用
- 不需要列出所有方法，只列出对外最重要的几个

## 重要方法判定规则

AI 在编码完成后，按以下规则自动判定方法是否为"重要方法"（**满足任一即判定为重要**）：

| # | 判定维度 | 条件 | 示例 |
|---|---------|------|------|
| R1 | 数据复杂度 | 涉及 ≥2 个数据库表的查询/更新/插入操作 | 从 A 表查数据→更新 B 表 |
| R2 | 状态机 | 包含 status/state 字段的条件赋值或状态转换逻辑 | 审批流中 status 从 PENDING→APPROVED |
| R3 | 外部依赖 | 调用 Feign 接口 / 第三方 API / MQ 发送 / RPC | 调用 OMS 系统同步数据 |
| R4 | 代码规模 | 方法体有效代码行 ≥ 30 行（不含空行、注释、单行 getter/setter） | 复杂的业务编排方法 |
| R5 | 接口可见性 | @RestController / @FeignClient 中的公共方法 | 对外暴露的 API 端点 |
| R6 | 事务边界 | 标注 @Transactional 的方法 | 涉及多表写入的事务方法 |
| R7 | 单据生命周期 | 涉及 create/submit/approve/reject/withdraw/cancel/close 等生命周期方法 | 单据提交、撤回、审核 |
| R8 | 处理管道 | 包含 ≥3 个数据处理步骤的方法（即使不满足 R1-R7） | 数据清洗→转换→入库 |

**判定时机**：方法编码完成后立即判定，不等到 `/withFinish` 时才补。

## IMPORTANT 标记机制

### 标记语义

| 标记 | 写入者 | 含义 | Agent 行为 |
|------|--------|------|-----------|
| `/** IMPORTANT */` | AI (TL) | AI 判定此方法重要，已生成全流程注释，人工审核时请重点关注 | 写入标记 + 全流程注释 |
| `/** IMPORTANT TODO */` | 人工 | 此方法需要 AI 分析并生成全流程注释 | 检测到后提醒用户使用 `/withAnnotate` |

### 标记位置

标记写在方法注释的紧上方（独占一行），紧随 `/** IMPORTANT */` 之后是方法注释或方法签名：

```java
/** IMPORTANT */
/**
 * 同步OMS订单数据（支持日期范围或天数）
 * <p>
 * 整体逻辑说明：
 * ...
 */
public SyncResultVO syncOmsOrder(SyncReqVO syncReqVO) {
```

对于尚无注释的方法（IMPORTANT TODO 场景）：

```java
/** IMPORTANT TODO */
@Override
public void processOrder(OrderVO order) {
    // 人工不理解这段逻辑
}
```

### IMPORTANT TODO → IMPORTANT 转换协议

1. Agent 检测到 `/** IMPORTANT TODO */` → 读取方法完整代码
2. 按"重要方法判定规则"（R1-R8）确认该方法是否为重要方法
3. 生成全流程注释（层级 2）+ 标准 JavaDoc（层级 1，如果缺失）
4. **穿透分析**：如果该方法直接调用的其他方法也满足重要判定规则但缺少注释 → 一并生成注释 + `/** IMPORTANT */`
5. 将所有**已完成分析**的 `/** IMPORTANT TODO */` 改为 `/** IMPORTANT */`
6. **最终目标**：代码中 **零 `/** IMPORTANT TODO */` 残留**

## AI 编码行为约束

### 编码时必须做

1. **公共接口注释**：所有 Controller/@FeignClient/Service 接口的 public 方法 → 生成标准 JavaDoc（层级 1）
2. **重要方法判定**：编码完成后自动对照 R1-R8 逐项检查
3. **全流程注释**：判定为重要方法 → 生成层级 2 全流程注释 + `/** IMPORTANT */` 标记
4. **类级注释**：新增的 Service/Controller/组件类 → 添加层级 3 类级注释

### 读到 IMPORTANT TODO 时

TL 在日常工作中读到包含 `/** IMPORTANT TODO */` 的代码时：
- **口头提醒**用户："发现 N 处未分析的 IMPORTANT TODO 标记，建议使用 `/withAnnotate` 分析"
- **不自动执行分析**（允许用户自主选择批量处理时机）
- 用户确认后 → 执行 `/withAnnotate`

### 不要求做

- 不对已有代码批量补全注释（除非用户明确要求）
- 不对 getter/setter/简单的工具方法加全流程注释
- 不为满足 R1-R8 但不属于"业务代码"的纯技术方法（如框架初始化、线程池配置）加 IMPORTANT 标记——TL 可根据上下文自行判断豁免
