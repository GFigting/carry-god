# 产物工件 (Artifact) 管理规范

## ⚠️ 强制总则

**任何角色在任何任务中产出的任何非代码文档，必须写入 `A.目标体系/GOAL-XXX/产物/{任务序号}/` 目录，严禁直接写入项目目录。**

此规则覆盖所有角色（TL/SA/BE/FE/QA/CR/OPS/PM 等）和所有文档类型（实施计划、修改计划、技术方案、评审报告、API 文档、设计文档、接口文档、会议纪要、架构图等 .md/.drawio 及任何非代码格式文件）。

**SQL 脚本例外**：DDL/菜单 SQL/数据迁移脚本等 `.sql` 文件视为代码类产物，直接写入项目 SQL 目录（查项目注册表 `sql_dir` 字段，如 `fms-sql/`），命名格式 `V{YYYYMMDD}_{动作}_{模块名/表名}.sql`（动作: `add`=增表 / `mod`=改表 / `del`=删表）。不受产物工件系统管理，由项目 Git 直接跟踪。TL 默认只新增本轮 SQL，不直接修改本轮对话以外的既有 SQL；除非人类明确指出可修改，或本轮目标就是把多个 SQL 汇集成一份。

任务确认完成后，由 Tech Lead 按 `sync_phase` 规则统一同步到项目 `docs/`。Agent 或 subAgent 不得自行同步。

**计划产物特殊规则**：当用户要求生成计划时，计划必须先写入本目录，frontmatter 使用 `status: in_review`。用户未确认前，不得依据该计划实施修改。计划正文必须从项目交付视角说明页面入口、按钮、筛选项、弹窗、列表列、后端接口、权限菜单 SQL、表字段、字典/枚举、DO/VO/DTO 和接口入参出参等影响。

---

## 概述

产物工件系统统一管理 Agent 生成的非代码类产出物，解决以下问题：

1. **命名规范**：统一命名规则，便于检索和归类
2. **存储位置**：文档在框架内迭代，流程结束后按需同步到项目，避免污染项目仓库
3. **多项目管理**：通过 frontmatter 承载项目归属，通过目录承载任务归属

代码类产出（.java/.vue/.ts 等）不受此系统管理，直接写入项目源码目录。

## 命名规范

### 格式

```
[GOAL{NNN}]-[{任务序号}-{子序号}-{产物序号}]-ART-{角色}-{描述}.{扩展名}
```

| 组成部分 | 说明 | 示例 |
|---------|------|------|
| `[GOAL{NNN}]` | 所属 Goal 编号 | [GOAL101] |
| `[{任务序号}]` | Goal 内任务递增序号（2位） | 01 |
| `[{子序号}]` | 任务内子任务序号，`00`=无子任务 | 00, 01 |
| `[{产物序号}]` | 子任务内产物递增序号（2位） | 01, 02 |
| `ART` | 固定前缀 | ART |
| `{角色}` | 角色缩写（见下方映射表） | TL, SA, BE, FE |
| `{描述}` | 简洁中文名，与产出物实际名称一致 | 技术方案设计 |
| `{扩展名}` | 文件实际格式 | .md, .sql, .drawio |

### 示例

```
[GOAL101]-[01-00-01]-ART-TL-实施计划.md
[GOAL101]-[01-00-02]-ART-CR-计划审核报告.md
[GOAL101]-[02-01-01]-ART-BE-DDL脚本.sql
[GOAL999]-[01-00-01]-ART-TL-问题排查报告.md
```

### 设计理由

| 维度 | 说明 |
|------|------|
| Goal 前置 | `[GOAL{NNN}]` 开头，文件名即知归属，无需打开父目录 |
| 层级编号 | `[任务-子-产物]` 三段精确锁定产出位置 |
| 排序友好 | 天然按 Goal → 任务 → 产物排序 |
| 工具兼容 | 括号前缀 + 中文描述，平衡兼容性与可读性 |
| 全局唯一 | `[GOAL][层级]-ART-{角色}` 组合保证不冲突 |

每个产物文件使用标准化 frontmatter（模板见 `.obsidian/templates/tpl-artifact.md`）：

```yaml

type: artifact
artifact_id: "[GOAL101]-[01-00-01]-ART-TL-实施计划"
name: "技术方案设计"
task_id: "[GOAL101]-[01]"
goal_id: "GOAL-101"

# 归属
role: "技术负责人"
role_prefix: "TL"
project: "fms-rear"
module: "对账结算中心"

# 生命周期

# 同步
sync_target: "fms-rear/docs/design-reconciliation-center.md"
synced_at: ""
sync_phase: "task_done"    # phase_done | task_done（默认）

# 元数据
created_by: ""             # Agent ID
created: "2026-06-12"
updated: "2026-06-12"

tags:
  - type/artifact
  - status/draft
  - role/tech-lead
  - project/fms-rear
  - module/对账结算中心
  - task/[GOAL101]-[01]
  - goal/GOAL-101
---
```

## 生命周期

```
draft ──→ in_review ──→ approved ──→ synced
  │           │            │
  └── 可随时回到 draft 修改 ──┘
```

| 状态 | 含义 | 触发者 |
|------|------|--------|
| `draft` | 草稿，Agent 初始写入 | Agent |
| `in_review` | 等待人类审核 | Agent 完成后标记 |
| `approved` | 审核通过，内容冻结 | 人类 |
| `synced` | 已同步到项目 docs/ | 主会话（自动） |

纯技术性产物（参考代码指南、API 文档等）可由 Agent 直接设为 `approved`，跳过 `in_review`。实施计划、修改计划、迁移计划等计划类产物必须保持 `in_review`，直到用户明确确认。

## 任务与产物关联

### 任务 frontmatter 新增字段

```yaml
# tpl-task.md 新增
artifacts:
  - artifact_id: "[GOAL101]-[01-00-01]-ART-TL-实施计划"
    status: "approved"
    sync_target: "fms-rear/docs/xxx.md"
```

### phases[].artifacts 引用

```yaml
phases:
  - phase_id: P0
    status: done
    artifacts:                          # 新增
      - "[GOAL101]-[01-00-01]-ART-TL-技术方案"
      - "[GOAL101]-[01-00-02]-ART-BE-DDL脚本"
    output: "技术方案 + DDL脚本"         # 保留，作为兜底文本
```

向后兼容：`output` 字段保持不变，旧任务继续使用。`artifacts` 为可选字段。

## 同步机制

### 触发时机

由产物 `sync_phase` 字段控制：

| sync_phase | 触发条件 | 适用场景 |
|-----------|---------|---------|
| `task_done`（默认） | 任务 status 变为 done | 需要多轮迭代的文档 |
| `phase_done` | 阶段 status 变为 done | 下游依赖的产物（如 API 接口文档） |

### 同步规则

1. **前置条件**：`status: approved` 且 `sync_target` 非空
2. **操作**：复制文件到 `{项目根目录}/{sync_target}`
3. **冲突处理**：目标已存在时，对比内容 → 相同则跳过，不同则生成 `.conflict` 文件
4. **更新**：`status: synced`, `synced_at: "{日期}"`
5. **代码文件**：`sync_target` 为空 → 已经在项目目录中，无需同步

### 同步执行者

主会话（时间线管理者），非 Agent。

## 代码 vs 文档的产出路径区分

| 产出类型 | 写入目标 | 管理方式 |
|---------|---------|---------|
| Java/Vue/TS 等源码 | 直接写入项目 `src/` 目录 | 不受产物工件系统管理 |
| 实施计划/修改计划/迁移计划 | `A.目标体系/GOAL-XXX/产物/{任务序号}/`，`status: in_review` | 先审核，确认后实施 |
| 技术方案/评审报告/API 文档 | `A.目标体系/GOAL-XXX/产物/{任务序号}/` | 产物工件系统管理 |
| SQL 脚本（DDL/菜单/数据迁移等） | 项目 SQL 目录（查项目注册表 `sql_dir`），命名 `V{YYYYMMDD}_{动作}_{模块名/表名}.sql` | 项目 Git 管理 |
| 目标级工作记录 | `A.目标体系/GOAL-XXX/` | 轻量日志（见下方） |
| 知识沉淀（可跨任务复用） | `知识沉淀/` 对应子目录 | 知识库管理 |
| 配置/脚本 | 直接写入项目对应目录 | 不受产物工件系统管理 |

## 目标级工作记录 (GOAL)

不同于任务级产物（ART-xxx 命名规范 + 完整 frontmatter），目标级工作记录是一种**轻量工作日志**。用途：指定某目标进行开发时，记录各分步的修改要求和完成情况。

### 目录结构

```
A.目标体系/GOAL-XXX/
└── 工作记录.md          ← 一个目标一个文件
```

### 格式

```markdown
# GOAL-001 工作记录

## Step 1: {分步描述}
- 要求：{要做什么}
- 状态：[x] 已完成
- 实现：{简述做了什么、怎么做的}

## Step 2: {分步描述}
- 要求：{要做什么}
- 状态：[ ] 未完成
- → 复杂，已转为任务 [[TASK-2026-XXX]]
```

### 规则

1. 一个目标一个 `工作记录.md`，分步追加
2. 每个分步只需记录：**完成状态** + **实现简述**
3. 简单分步 → 直接在 Step 里记录完成
4. 复杂分步 → 转为正式任务，在 Step 里记下任务链接
5. 无 frontmatter 要求，无命名规范，极简
6. 人类和 AI 均可写入

### 与任务产物的区别

| 维度 | GOAL 工作记录 | TASK 产物工件 |
|------|-------------|--------------|
| 粒度 | 粗（分步 = 一组相关改动） | 细（单一交付物） |
| 格式 | 自由 markdown | ART-xxx 命名 + frontmatter |
| 生命周期 | 无（勾选即完成） | draft → in_review → approved → synced |
| 维护者 | 人类 + AI | 主要是 Agent |
| 转任务 | 复杂分步转为 TASK | —

## Agent 产出规则摘要

1. **文档产物** → Write 到 `A.目标体系/GOAL-XXX/产物/{任务序号}/` 按命名规范创建
2. 使用 `tpl-artifact.md` 模板填写 frontmatter
3. 完成后设 `status = in_review`（需审核）或 `approved`（纯技术产物）
4. 同步由主会话执行，Agent 不自行同步到项目
5. 代码文件直接写入项目目录，不受产物系统管理
6. **SQL 脚本直接写入项目 SQL 目录**（查项目注册表 `sql_dir` 字段，如 `fms-sql/`），命名格式 `V{YYYYMMDD}_{动作}_{模块名/表名}.sql`（动作: `add`=增表 / `mod`=改表 / `del`=删表）。SQL 脚本视为代码类产物，由项目 Git 管理，不走产物工件系统；历史 SQL 默认不回改，新修正用本轮补丁 SQL 承载。
7. **计划类产物先审核后实施**：用户要求计划时，先写入 Markdown 产物并设为 `in_review`；用户确认前禁止实施修改。计划内容必须从项目角度描述新增页面、按钮、后端能力和数据结构变化，不能只列技术文件。
