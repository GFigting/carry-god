- **最近完成**：2026-06-23 — /withGrill 目标澄清能力（P9）、TL编写与finish能力增强（P8）、知识库体系区分（P2）
- **当前分点**：

    - [ ] 3. 目标体系拓展：不再局限于单工作空间，任何事都可以是目标
    - [x] 4. 需求收件箱： 接收了框架外的资料后 如何和内化成某个goal或者对应的task。
    - [ ] 5. 异步联动级目标体系：实现目标分发，让团队成员协同同一任务；

    - [ ] 10.自记忆框架改进能力
	    - [ ] agent工作过程中肯定偶尔做出的产物和人想象的不太一样，用户会让agent根据上下文提出agent自己可能误解的问题。不过现在这些问题都是人分析后让teacher改的。其实完全可以在A.teacher分析下 构建一个agent的问题反馈集合，teacher就可以看到每个对话下agent自己总结的问题 并进行修改了。
	    - [ ] 这个概念很像hermes 的自进化 但是不太一样的是：提出“需要进化”的 目前仍然是人类，因为太多技能太多文档 压力最后还是给到ai自己。多不代表好，频繁更新不代表优秀。稳稳地让人类成长并让ai也轻松，也是这个框架的隐藏初心。
    - [x] 11.withGrill的“内行无了解无上下文多视角提问” 划定目标
	    - [x] withGrill确实不该直接修改goal的内容，在指定withGrill门禁后，需要单独建一个grill明细的文件，由人来答疑，把所有的问句改成陈述或者标为后期待定。然后再由agent按清晰明确的格式 将内容更新回目标总览，并进行后续的步骤。（更新的内容可以参考GOAL-002）
	    - [x] grill可以提供多个角度：
		    - [x] 1.侧重业务侧用户的使用角度：更看重功能具体提供了什么价值，操作是否清晰明了，能否借由这种功能解决真正的业务痛点；并猜想功能可以和什么功能发生组合就能提供更大助力，
		    - [x] 2.侧重系统设计的TL角度：这点目前按TL处理事情的视角就已足够。
    - [ ] 12.框架更新等标准脚本
    - [ ] 13.框架桌面程序化（Goal Kernel 可视化外壳）：
        - **目标**：将 Goal 管理从纯文本编辑升级为结构化、可查询、可自动化的通用目标内核；桌面程序只是第一种交互外壳
        - **路线**：Goal Kernel → SQLite 本地数据源 → Electron/Vue 桌面外壳 → Agent API → 后续团队协作/服务端数据库
        - **前置草案**：`A.Teacher分析/改造草案/改造草案-DREAM001-P13-Goal领域模型与SQLite内核.md`（Goal 通用定义+SQLite schema+标签/状态结构化）
        - **桌面草案**：`A.Teacher分析/改造草案/改造草案-DREAM001-P13-桌面程序Goal管理.md`（桌面程序作为 Goal Kernel 外壳）
        - **技术栈**：Electron + Vue 3 + TypeScript + Pinia + SQLite，AI 全权选型+全权维护
        - **关键设计**：SQLite 承载真实数据；Markdown/Obsidian 降级为导入导出与人类可读视图；Goal/分点/任务/产物/答疑/状态/证据链全部结构化
        - **补充**：
	        - Goal 是通用工作对象，不仅服务研发任务；
	        - 要支持任务生命周期、分点进度、多维度交付状态、阻塞、证据链；
	        - 对分点的答疑不直接混在目标中，而是形成结构化 `qa_record`；
	        - 文本状态标签只是过渡格式，最终映射到 `dimension_status` 和 `status_event`；
        - [ ] 13.0 Goal 领域模型与 SQLite schema 前置设计
