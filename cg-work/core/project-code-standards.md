# 项目通用代码规范

## 定位与优先级

本规范是项目规范缺失或未覆盖时的跨语言兜底规则，不替代项目仓库已经声明的约定。优先级为：用户明确要求 > 项目规则与工具配置 > 本规范 > 工作流与技能建议。项目规则与本规范冲突时，采用项目规则，并在任务记录中说明。

项目接入或开发开始时，先读取项目的 `AGENTS.md`、`CODING_STANDARDS.md`、`CONTRIBUTING.md`、README 及格式化、Lint、测试和构建配置；不要仅以本规范替代这些来源。

## 应用时机

本规范在实施过程中直接适用，而不只是代码审查清单：

1. **计划前**：识别项目已有规范、受影响模块和可执行验证命令；明确哪些规则由项目覆盖、哪些采用本规范兜底。
2. **编码时**：按本规范的基线组织名称、职责、边界、错误处理、类型和注释；每次准备交付的代码修改必须经过项目格式化器，必要的意图注释必须随实现一并写入。发现需要为既有不规范代码扩大改动范围时，先评估是否属于当前需求，避免借机进行无关重构。
3. **提交前**：执行项目格式化、静态检查与相关测试，并对改动逐项自查本规范；代码审查用于独立确认，不替代实施阶段的遵循。

## 常量化前置检查

“使用常量，不要硬编码”不是只在审查时处理的意见，而是计划、编码和提交前验证的前置要求：

1. **计划阶段**：识别本次变更中的状态值、类型值、路由片段、接口路径、阈值和重复业务文案，记录哪些需要抽为常量、枚举、领域值或配置，以及哪些属于允许的局部值。
2. **编码阶段**：先定义已识别的常量、枚举或领域值，再接入业务逻辑；新发现的重复业务字面量应立即回到同一判断，不等到审查阶段返工。
3. **提交前**：优先运行项目已有的 ESLint、Checkstyle、静态扫描或格式化规则；工具未覆盖时，对当前差异做定向人工检查，并在任务计划的「标准编码前置检查」段落中区分自动通过、人工通过和不适用。
4. **审查阶段**：复核前置判断、工具结果和例外理由；审查不应是首次发现常量化问题的环节。

以下内容通常可以保留字面量，但应在必要时说明理由：一次性展示文案、测试数据、协议固定值、模板内容、局部且语义明确的值，以及由项目规范明确允许的配置值。不要为了形式统一，把没有业务含义的每个字面量都包装成常量。

## 可追溯记录

- 项目初始化时，在 `project-context.yaml` 的 `documentation.development_standards` 中登记项目专属代码规范文件（例如 `AGENTS.md`、`CODING_STANDARDS.md`、`CONTRIBUTING.md`）。历史上下文可继续使用 `coding_standards.files`；每个登记路径必须存在。
- 实施任务的计划或验证记录必须说明：本次读取的规范来源、已执行的格式化/Lint/测试命令，以及因环境或项目约定未执行的项目和原因。任务 YAML 无需新增必填字段，避免要求历史任务迁移。

## 必须遵守的基线

1. **可读性优先**：名称必须表达业务含义或技术职责；一个模块、类型或函数只承担一个可解释的主要职责。不得为尚未存在的需求引入抽象、开关或扩展点。
2. **边界明确**：外部输入、空值、异常、异步失败和资源生命周期必须在所属边界显式处理。不得吞掉异常或用默认值掩盖失败；确需降级时，保留可观察的错误信息或状态。
3. **避免隐性耦合**：重复出现且有业务含义的字面量应命名为常量、枚举或领域值；跨模块传递的一组稳定字段应优先形成明确类型或对象。接口变更必须评估调用方与数据兼容性。
4. **必要注释**：不要求逐行注释，但公开接口和公共类型、非直观业务规则或状态转换、异常降级或边界条件、临时兼容逻辑必须说明意图、约束或取舍。注释不得只复述代码字面行为。
5. **强制格式化**：修改代码后、进入审查前必须运行仓库已配置的格式化器（例如 Prettier、Spotless 或等效工具），并以该工具的输出为准，不以手工排版替代。没有格式化器时，任务验证记录必须明确“缺少自动格式化工具”及原因，不得表述为格式检查通过。
6. **遵循自动化约束**：使用仓库已配置的静态检查和测试命令。格式化、Lint、测试、构建和浏览器验收各自证明不同事实；不能以其中一个替代另一个。

## 分层、事务与错误处理

1. **依赖方向**：保持项目既有分层。入口层负责协议适配、参数校验和响应映射；应用/业务层编排用例与事务；领域逻辑表达业务不变量；持久化与外部系统访问通过既定接口或适配层完成。不要让领域逻辑依赖 HTTP、ORM、数据库连接或 UI 框架。
2. **边界校验**：在外部输入进入业务层时完成格式、范围、权限和必填校验。内部方法仍应维护自身不变量，不要把所有校验堆在控制器或页面中。
3. **事务范围**：事务覆盖一个完整业务用例所需的原子写操作，避免在事务中执行网络请求、长时间计算或等待用户输入。多系统写入不能假设数据库事务能提供分布式原子性，应明确补偿、幂等或重试策略。
4. **错误语义**：区分用户输入错误、业务拒绝、资源不存在、并发冲突、依赖失败和程序缺陷。保留原始异常作为 cause 或结构化日志字段；不得捕获后静默忽略，也不得把内部堆栈、SQL、凭据或个人数据直接返回给用户。
5. **异步与资源**：异步任务必须有明确失败传播、取消或超时策略；文件、流、连接、锁等资源要在所有成功和失败路径释放。后台任务应记录可关联的任务标识和最终状态。

## Java 规则

仅在 Java 项目且项目规范未覆盖时采用：

- 类、方法和字段使用能表达职责或领域含义的名称；常量使用项目约定的命名格式。避免无意义缩写和仅以 Util、Manager、Helper 命名的宽泛类型。
- 面向接口只用于真实替换边界、外部依赖或明确的多实现契约，不为每个类机械创建接口。
- 集合和 DTO 的可空性、可变性与所有权要明确；不暴露可被调用方随意修改的内部可变集合。
- 资源使用 try-with-resources 或项目提供的等效生命周期管理；线程池、异步执行器和客户端由明确所有者创建、配置和关闭。
- 持久化实体与 API 请求/响应模型按项目分层约定使用；避免把 ORM 实体直接作为外部契约。
- 捕获异常时只在能够恢复、转换语义或补充上下文的边界处理；重新抛出时保留 cause。禁止空 catch 和仅打印后继续。

## TypeScript 与 JavaScript 规则

仅在 TypeScript/JavaScript 项目且项目规范未覆盖时采用：

- 优先使用项目已有的模块系统、类型检查器和格式化配置；新增公开边界时为输入、输出和共享数据结构提供明确类型。
- 避免用 any 关闭类型检查；不可信输入从 unknown 开始，在边界解析和收窄。类型断言只用于静态分析无法表达且已有运行时保证的情况。
- Promise 必须被等待、返回或显式处理；禁止未处理的拒绝和无意的 fire-and-forget。后台运行必须有错误观察和生命周期管理。
- 使用严格相等和显式空值处理；不要用会把合法的 0、false 或空字符串误判为缺省值的真假值判断。
- 浏览器 DOM、网络、存储和服务端运行时能力应留在对应适配边界；共享业务逻辑不直接依赖全局环境。
- 公开函数应声明可观察的错误行为；不要用宽泛 catch 返回伪造成功值或空对象掩盖失败。

## SQL 与数据库规则

仅在项目使用 SQL 或直接访问数据库时采用：

- 查询必须参数化；动态表名、列名、排序字段或操作符不能用参数占位时，必须通过封闭白名单映射，不能直接拼接外部输入。
- 写出查询所需字段，避免无意的 SELECT *；分页必须有稳定排序。对循环内查询、重复往返和无界结果集保持警惕，按数据量和执行计划验证索引及查询形态。
- 新增或修改索引前说明目标查询和预期收益；考虑索引对写入、存储和迁移锁定的成本。不要仅凭字段名推断索引必要性。
- DDL/DML 变更脚本应可审查并符合项目迁移工具和命名规则。明确执行顺序、适用环境、重复执行行为、锁表/耗时风险和回滚或前向修复方案。
- 破坏性变更采用可分阶段发布的兼容路径：先扩展、迁移和验证，再删除旧结构；禁止未经确认直接清空、覆盖或转换已有数据。
- 大表回填应分批、可续跑并可观测；避免单个长事务锁住生产表。数据迁移应校验总量、关键约束和抽样结果，失败时保留明确停止点。
- SQL 脚本不得包含真实密码、令牌或不必要的生产数据。连接配置与脚本分开管理，执行前遵守项目环境和授权要求。
- 读写必须遵守项目事务边界、租户/权限过滤、软删除和数据范围约束；原生 SQL 不得绕过这些规则。

## 测试与改动范围

- 新增或修复可观察行为时，为关键成功路径、失败路径和边界条件提供匹配层级的测试；纯重命名或格式调整不要求机械增加测试。
- 数据库查询测试应覆盖筛选条件、排序、分页、空结果和权限/租户边界；迁移应有可执行验证或明确的人工核验步骤。
- 修改接口、持久化结构或共享类型时，检查所有调用方、序列化格式和兼容边界。测试替身不得掩盖真实契约差异。
- 修改范围保持在需求所需模块。发现邻近缺陷时记录并单独拆分，除非修复它是本次变更正确运行的必要条件。

## 审查方式

- 前四项及格式化要求是审查基线：发现违反时应给出具体代码位置、风险和修正建议；缺少必要注释不是泛泛建议，而是需要修正的问题。
- 代码风格中的纯偏好（例如可选换行形式）不作为独立问题；以项目格式化工具结果为准。
- 代码坏味道只作为需结合上下文判断的建议，不把语言风格偏好上升为硬性违规。

## 参考来源与取舍

- [阿里巴巴 Java 开发手册](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)：参考其对命名、异常处理、并发、集合、数据库与安全风险的工程化约束。仅在 Java 项目且项目规范未覆盖时采用相关条目。
- [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html)：参考其一致性、可维护性和文档化原则；该指南明确说明可选格式化示例不应被强制化。
- [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html)：参考其类型表达、模块边界、命名和可读性原则；仅在 TypeScript 项目且项目规范未覆盖时采用相关条目。

框架只保留上述可执行摘要和来源链接，不复制外部手册全文。语言专属规则应由项目或其专属技能声明，避免把 Java、TypeScript 或其他语言的细节错误施加到所有项目。
