# 命名与提交

- 目录和普通文件使用 `kebab-case`。
- 技能目录、技能 ID 和流程引用名称保持一致。
- 项目 ID 使用小写 `kebab-case`；任务 ID 使用 `<YYYY-MM-DD>-<task-slug>` 格式，例如 `2026-09-10-project-initialization`，并在对应项目目录内唯一。
- `README.md`、`AGENTS.md`、`CLAUDE.md`、`SKILL.md` 和 `VERSION` 是约定的固定名称。`CLAUDE.md` 只是 Claude 系 Agent 的路由入口，指向 `AGENTS.md`，不复制规则。
- `cg-work/` 下框架内容默认提交。
- `local/projects/` 下真实项目内容不提交。
- 不提交凭据、临时调试文件、项目业务数据或未经确认的生成产物。

## 测试类与测试方法生成标准

- 只有在变更产生新的可观察行为、业务规则、边界条件、异常路径、权限/兼容性约束，或修复了需要防止回归的问题时，才新增测试类或测试方法。
- 优先在已有测试类中补充同一职责的场景；只有测试对象、生命周期、依赖隔离或断言边界明显不同，才新建测试类。
- 不为 getter/setter、简单映射、直通委托、常量读取、框架样板或一行显然正确的逻辑单独生成测试类；这类逻辑只有在承载业务约束、历史缺陷或对外契约时才需要测试。
- 测试应验证业务可观察结果或稳定契约，不应只验证私有实现细节、调用次数或机械转发；每个测试类和方法都应能说明独立保护价值。
- 缺陷修复命中硬三类（数据不可逆、红线、真会悄悄坏的核心逻辑，见 [最小充分流程](operating-model.md#最小充分流程)）时必须补充能复现原问题的回归测试；其余修复以人工验收为准。无法自动化或不自动化时，必须在验证记录中说明原因、替代验证和风险。

## 原项目提交口径

当提交目标是原项目业务仓库时：

- 测试文件默认保留，不因提交动作自动删除或排除。仅覆盖 getter/setter、简单映射、直通委托、样板代码或无独立回归价值的简单逻辑测试类和测试方法，应视为可清理内容；确认其没有独立保护价值且用户或任务范围明确授权清理后，才允许删除。删除前先完成必要验证，在任务验证或交接记录中保存删除清单（含类/方法），并复核提交差异。
- 测试文件包括测试目录（如 `test/`、`tests/`、`__tests__/`、`spec/`、`specs/`）及其全部内容，文件名包含 `.test.` 或 `.spec.` 的测试源码，以及测试夹具、快照、模拟数据和测试配置；项目已有约定更宽时，以项目约定为准；
- 框架自身提交：保留 `cg-work/test/` 中仍有保护价值的测试，仅删除已确认无效、临时或重复的测试，并在任务验证记录中说明删除理由；
- 将最新 SQL 合并到正式脚本，清理同一变更的冗余脚本，保留历史任务仍引用且仍有独立价值的脚本；
- 清理与本次变更直接相关的冗余代码、字段、注释和配置，但不得借机删除无法确认归属的用户改动；
- 提交前完成新鲜验证、差异检查和任务记录校验；
- `submit-branch` 提供 `--list-tests` 只读列出已跟踪测试文件，提供 `--remove-test` 显式删除单个测试文件；工具不得自动扫描后删除。
- “提交”仅表示创建本地 Git commit，不自动推送、合并、部署或删除分支。

“原项目提交”仅指提交项目业务仓库；该规则不适用于 `cg-work` 框架自身。框架自身应保留仍有保护价值的回归测试，仅删除已确认无效、临时或重复的测试；任何场景都不授权自动删除未确认归属的其他目录或改动。
