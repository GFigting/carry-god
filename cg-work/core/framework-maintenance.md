# 框架维护

新增或修改规则和工作流时，只修改其唯一来源，并同步更新版本、README 和相关引用。新增镜像技能必须完整复制上游目录，不能修改、翻译或补充其中的文件。

技能分为三类：框架自有技能、原始镜像技能和框架本地化技能。原始镜像必须完整登记来源映射；框架自有技能与框架本地化技能由 cg-work 维护，不登记为镜像。框架本地化技能可以复用上游方法，但必须在技能正文声明本地覆盖规则与其唯一来源。

## 框架演进不变量

优化框架规则、工作流、模板、校验器、目录约定或框架自有技能时，必须记录证据、受影响的唯一来源、兼容性等级、迁移或替代说明与验证范围。

框架内容不得混入项目业务规则、真实需求、密钥、运行日志或生产数据。项目业务代码的结构调整不属于框架维护，使用 `framework:refactor`。

每次变更必须运行 `npm run check`。项目上下文变更后运行 `node scripts/check-project.mjs <path>`。废弃且无运行时消费者的文件可以直接删除；历史任务的变更清单和叙述属于审计记录，不要求为清理路径提及而改写。框架自身不保存项目业务资料。

框架优化在用户验收且完成新鲜验证后，必须创建 Git 提交。提交前先检查工作区，仅暂存当前任务涉及的框架文件，不得使用 `git add .`：业务项目在 `local/projects/<project-id>/` 下的需求包、任务、报告和运行产物一律不得混入框架提交；框架受管项目 `local/projects/cg-work/` 的记录虽然同在一个仓库并随框架提交，但必须与规则改动分成不同 commit，便于回溯。若目标文件混有无法安全拆分的无关修改，保持任务在 `review` 并说明阻塞原因。

提交收尾的仓库边界（测试处理、SQL 整合、冗余清理、文档同步、校验顺序和授权范围）以 [命名与提交](naming-and-submission.md#原项目提交口径) 为唯一来源，本文件不重复正文。框架维护只额外要求：只暂存当前任务涉及的框架文件，并在提交后重新运行 `npm run check`。

产物存放位置不在此重复正文：任务记录、框架设计产物、大任务主从拆分的唯一位置分别见 [工作模型](operating-model.md) 的“任务证据生命周期”与“大任务主从拆分”、[README](../README.md) 的“目录边界”以及 [项目上下文](project-context.md) 的原型登记；新增或调整位置规则时只改唯一来源。原型不单独建档：实现契约写入计划记录的 `## 原型实现契约` 章节，采纳结论写入评审记录的 `## 原型采纳` 章节，不得以“仅供参考”替代采纳结论，字段与骨架见 [工作模型的原型与任务记录](operating-model.md#原型与任务记录)。

存量路线图只保存 `roadmap.yaml`、`coverage.md` 和 `closure.md` 三件套，双轨保留、不再新建；新大任务的拆分与关闭记录在主任务的 `task.yaml` 与 `plan.md`（见 [工作模型](operating-model.md#大任务主从拆分)）。不得复制原始需求或迁移任务目录；新增路线图字段必须保持可选，避免要求历史任务迁移。

任务学习闭环的唯一规则来源是 `core/continuous-learning.md`。框架级经验的提升必须保留来源任务、证据和适用范围；不要把单次执行中的猜测直接固化为通用规则。

`VERSION` 使用语义化版本：破坏现有流程、模板或技能调用约定时升级主版本；新增兼容能力时升级次版本；仅修正文档或校验时升级修订版本。
