# 框架维护

新增或修改规则和工作流时，只修改其唯一来源，并同步更新版本、README 和相关引用。新增镜像技能必须完整复制上游目录，不能修改、翻译或补充其中的文件；同时在 `scripts/check-skills.mjs` 添加来源与目标映射。

技能分为三类：框架自有技能、原始镜像技能和框架本地化技能。原始镜像必须登记并通过 `scripts/check-skills.mjs` 哈希校验；框架自有技能与框架本地化技能由 cg-work 维护，不登记为镜像。框架本地化技能可以复用上游方法，但必须在技能正文声明本地覆盖规则与其唯一来源。

## 框架演进不变量

优化框架规则、工作流、模板、校验器、目录约定或框架自有技能时，必须记录证据、受影响的唯一来源、兼容性等级、迁移或替代说明与验证范围。

框架内容不得混入项目业务规则、真实需求、密钥、运行日志或生产数据。项目业务代码的结构调整不属于框架维护，使用 `framework:refactor`。

每次变更必须运行 `npm run check`。项目上下文变更后运行 `node scripts/check-project.mjs <path>`，任务状态变更后运行 `node scripts/check-task.mjs <path>`。废弃内容保留替代说明，不删除仍被历史任务引用的文件。框架自身不保存项目业务资料。

框架优化在用户验收且完成新鲜验证后，必须创建 Git 提交。提交前先检查工作区，仅暂存当前任务涉及的框架文件，不得使用 `git add .`：业务项目在 `local/projects/<project-id>/` 下的需求包、任务、报告和运行产物一律不得混入框架提交；框架受管项目 `local/projects/cg-work/` 的记录虽然同在一个仓库并随框架提交，但必须与规则改动分成不同 commit，便于回溯。若目标文件混有无法安全拆分的无关修改，保持任务在 `review` 并说明阻塞原因。

提交收尾的仓库边界（测试处理、SQL 整合、冗余清理、文档同步、校验顺序和授权范围）以 [命名与提交](naming-and-submission.md#原项目提交口径) 为唯一来源，本文件不重复正文。框架维护只额外要求：只暂存当前任务涉及的框架文件，并在提交后重新运行 `npm run check`。

项目任务记录的唯一位置是 `local/projects/<project-id>/tasks/<task-id>/`。原始技能提出的其他计划或报告路径属于上游默认建议；在本框架中统一以任务记录为准，避免出现两份计划或验证报告。

框架设计产物的默认位置为 `local/projects/<project-id>/design/<design-name>/`，适用于单页面原型和不依赖业务仓库的多页面原型。依赖真实项目路由、组件或运行入口的多页面原型，可由用户选择放在关联项目的 `<project.root_path>/prototypes/<design-name>/`；此类路径必须登记在项目上下文的 `prototypes.paths` 中。根目录 `designs/` 不再用于新产物；已有产物只有在更新其任务引用后才可迁移，避免破坏历史任务。

大任务路线图的唯一默认位置为 `local/projects/<project-id>/roadmaps/<roadmap-id>/`。路线图只保存 `roadmap.yaml`、`coverage.md` 和 `closure.md` 等项目级索引；不得复制原始需求或迁移任务目录。新增路线图字段必须保持可选，避免要求历史任务迁移。

原型属于任务 Artifact，但不单独建档：实现契约写入计划记录的 `## 原型实现契约` 章节，采纳结论写入评审记录的 `## 原型采纳` 章节，两者都必须保留原型到实现和验证的映射；不得以“仅供参考”替代采纳结论。字段与骨架见 [工作模型的原型与任务记录](operating-model.md#原型与任务记录)。

任务学习闭环的唯一规则来源是 `core/continuous-learning.md`。框架级经验的提升必须保留来源任务、证据和适用范围；不要把单次执行中的猜测直接固化为通用规则。

`VERSION` 使用语义化版本：破坏现有流程、模板或技能调用约定时升级主版本；新增兼容能力时升级次版本；仅修正文档或校验时升级修订版本。
