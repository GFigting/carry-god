# 项目文档规范

本规范定义业务项目应维护的文档类别、文档与项目上下文的关联边界，以及文档的最低质量要求。它服务于项目接入、任务执行和交付审查，不要求每个项目一次性补齐全部文档。

## 1. 文档登记原则

项目上下文只登记执行任务时需要反复查阅、能够作为事实依据、并且预计在多个任务中保持有效的文档。文档数量较多时，优先登记总入口、类别入口和高频核心文档，任务按需沿索引加载叶子文档。

登记文档必须满足：

- 路径真实存在；除框架受管项目 `cg-work` 外，项目上下文中的文件和目录路径使用绝对路径；
- 有明确维护责任和适用范围；
- 内容描述稳定规则，而不是某一次任务的临时结论；
- 能帮助 Agent 或开发者作出实现、验证、运行或交付判断。

以下内容不登记到 `project-context.yaml` 的 `documentation`：

- 单个任务的 `plan.md`、`review.md`、`verification.md` 和 `handoff.md`；
- 原始需求、临时会议纪要和一次性排查记录；
- 构建产物、日志、截图和自动生成的大型文件；
- 密钥、令牌、密码、真实生产数据和完整个人信息。

单次需求与任务证据按任务生命周期保存；稳定规则应在任务结束时回写到对应的项目文档，并在必要时更新项目上下文关联。

## 2. 文档大类别

### 2.1 项目入口与协作规范

典型文件：`README.md`、`AGENTS.md`、`CONTRIBUTING.md`、分支和提交规范、代码审查规则。

最低内容：项目用途、仓库边界、常用入口、协作约束、提交和审查要求。项目规则文件登记在 `documentation.project_rules`；开发规范文件登记在 `documentation.development_standards`。

### 2.2 项目上下文与运行验证

典型内容：技术栈、依赖、环境变量说明、本地启动、构建、测试、健康检查和验证命令。

运行入口登记在 `runtime.entrypoints`，健康检查登记在 `runtime.health_checks`，验证命令登记在 `verification.profiles`。命令的唯一记录不应只存在于叙述性文档中。

### 2.3 业务与领域文档

典型内容：业务目标、术语表、角色与权限、核心流程、状态机、业务规则、异常场景和边界条件。

文档应说明规则适用对象、状态变化触发条件、拒绝条件和例外处理；不得只罗列页面或接口名称。

业务文档较多时，按业务领域或稳定能力分层组织，避免将所有文档平铺在同一目录。每个层级设置索引入口，例如 `docs/README.md`、`business/README.md` 和 `business/<domain>/README.md`。拆分依据应是相对稳定的业务主题，不按页面、接口或单次开发任务拆分。

每个稳定业务主题只保留一个权威文档来源。索引和其他文档通过链接引用权威来源，不复制整段规则；发现重复或冲突时，应明确保留哪个来源，并将其他内容改为引用或移除。文档入口应说明主题范围和下级索引，使读者能从总览定位到具体规则。

### 2.4 架构与模块文档

典型内容：系统架构图、模块地图、能力地图、模块职责、依赖关系、数据流和外部集成边界。

文档应说明模块拥有的职责、允许的依赖方向、跨模块调用方式和关键架构取舍。架构决策记录应保留背景、选项、结论和影响。

### 2.5 接口与数据契约

典型内容：OpenAPI、请求与响应字段、错误码、认证要求、兼容策略、事件、消息和定时任务契约。

每个对外契约至少应说明输入、输出、失败行为、权限、幂等性或重复投递处理，以及版本兼容要求。接口文档为空时，应明确记录为缺口，而不是用实现代码推测契约。

### 2.6 数据与数据库文档

典型内容：表结构、字段语义、主外键、唯一约束、索引、数据字典、迁移规范、初始化、历史数据迁移和回滚方案。

字段说明应区分技术类型和业务含义；状态、枚举和软删除语义应与业务文档保持一致。涉及删除、迁移或语义转换时，必须记录影响范围、回滚条件和验证方式。

`documentation.data` 关联长期有效的数据模型和数据库规则。可选的 `database.sql_paths` 只登记项目仓库中 SQL 脚本目录的位置，不重复登记规则文档、连接配置或执行命令。数据库连接/MCP 配置沿用项目既有规则和工具配置入口，命令与验证分别使用 `runtime`、`verification`。具体 SQL 变更脚本保存在项目仓库既有迁移目录或对应任务产物中，不复制进项目上下文；连接配置中的凭据须保持本地并遵守项目授权边界。

### 2.7 工程开发规范

典型内容：语言和框架规范、命名、分层、异常、日志、事务、查询性能、格式化、Lint、测试和构建要求。

项目专属规范登记在 `documentation.development_standards`。未覆盖的事项遵循 `core/project-code-standards.md`，不得在任务中临时创造与项目现有规则冲突的约定。

### 2.8 运维与运行手册

典型内容：部署、回滚、环境差异、配置、监控、告警、日志、健康检查、故障排查和应急处理。

运行手册应包含可执行入口、前置条件、观察指标、常见故障的判断路径和恢复步骤。生产操作边界应与安全规范和授权要求一致。

### 2.9 安全与合规

典型内容：认证授权、敏感数据分类、密钥管理、审计、数据留存、隐私和生产操作边界。

不得在文档中写入真实凭据或生产数据。对高风险操作，应明确授权人、审计要求、回滚或止损方式。

### 2.10 交付与变更记录

典型内容：路线图、发布说明、变更记录、架构决策、已知问题和遗留项。

项目级路线图按项目规则登记在 `product.roadmap_path`。单次需求、任务计划和验证证据仍保存在任务目录，不以路线图替代任务记录。

## 3. 项目上下文关联建议

建议按以下优先级关联：

1. 必须关联：项目入口与协作规范、工程开发规范、核心业务规则、核心架构说明、运行和验证入口。
2. 按需关联：接口契约、数据与数据库、运维、安全、交付与路线图文档。
3. 缺口记录：重要类别暂时没有文档时，在项目初始化或任务审查中记录缺口、影响和补齐计划，不伪造空文档。

项目文档路径统一登记在 `documentation` 下：`project_rules`、`development_standards`、`business`、`architecture`、`api`、`data`、`operations` 和 `security`。项目上下文另有 `runtime` 和 `verification` 字段记录运行入口与验证命令，路线图使用 `product.roadmap_path`；这些可执行配置和单一产物路径不重复登记为普通文档清单。`delivery` 不单独设为文档类别，路线图、任务证据、架构决策和发布记录分别遵循各自的权威存储位置。

同一文档只登记在一个 `documentation.*` 类别。每项记录包含 `path` 和 `load`：`always` 表示每项任务都读取，`when_relevant` 表示按任务主题读取。只在特定操作时需要的说明，应留在其专属入口（如 `submission.instructions`）；不再设置独立的 `required_context` 清单。

## 4. 命名规范

### 4.1 通用原则

- 目录和普通文件名使用小写 `kebab-case`，单词之间使用单个连字符；
- 名称使用稳定、可检索的业务或技术语义，避免 `misc`、`other`、`temp`、`new`、`final` 等无信息名称；
- 同一层级不得同时使用同义词或不同语言表达同一概念；
- 文件名应能表达文档主题，不把日期、作者或状态作为主题名称的一部分；
- 已发布或被引用的文档改名必须同步更新所有引用，不能只保留旧副本造成双重事实来源。

### 4.2 文档文件名

推荐使用 `<主题>.md`，例如 `business-glossary.md`、`order-lifecycle.md`、`module-map.md`、`api-contract.md`、`data-dictionary.md`、`deployment-runbook.md`、`security-baseline.md`。

同一主题存在多个相互独立的文档时，使用稳定的主题前缀加明确后缀，例如 `api-authentication.md`、`api-error-codes.md`。不要使用 `api-v2-final.md`、`最新接口.md` 这类把版本或状态混入文件名的方式；版本信息应写在文档正文或变更记录中。

### 4.3 目录命名

按文档类别组织目录时，目录名使用以下固定词汇：

- `business/`：业务与领域；
- `architecture/`：架构与模块；
- `api/`：接口与数据契约；
- `data/`：数据与数据库；
- `operations/`：运维与运行手册；
- `security/`：安全与合规；
- `delivery/`：交付与变更记录。

项目已有稳定目录结构时，不为追求统一而批量移动文件；新增文档遵循现有结构，并在项目文档入口中说明类别映射。

### 4.4 特殊名称

项目根目录入口可使用约定名称 `README.md`、`AGENTS.md`、`CONTRIBUTING.md`。这些是协作入口的固定例外，不作为普通主题文件名的通用模板。框架产物的任务 ID、项目 ID 和其他结构化标识继续遵循 `core/naming-and-submission.md` 及对应校验器规则。

## 5. 文档质量与维护

每份登记文档应有清晰标题、适用范围、维护入口和更新时间或版本信息。内容发生变化时，应检查项目上下文中的路径和相关任务规则是否仍然有效。

文档审查至少确认：

- 结论能追溯到代码、配置、接口、数据结构或已确认的业务事实；
- 示例、命令、路径和链接可执行或明确标注环境限制；
- 术语、状态、字段和权限在不同文档间一致；
- 已废弃内容有替代入口，不与当前规则并列生效；
- 文档没有凭据、生产数据或无必要的个人信息。

文档规范本身由 `cg-work` 框架维护；项目业务文档由关联项目维护。框架规则与项目规则冲突时，按项目规则优先级执行，并在任务记录中说明差异。
