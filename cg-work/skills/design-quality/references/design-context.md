# 设计上下文

## 为什么是硬前置

代码只记录"做了什么"，不记录"为谁做、要在什么情境里起什么作用、该有什么感觉"。跳过这一步，模型会退回训练分布的平均值：居中标题、三行副文案、一排图标卡、一点渐变——什么都没错，但没有一处是决定。

四项必须由人给出，**禁止从代码库推断感受与受众**；代码只用来排除已知事实（技术栈、已有色值、现有组件）。

## 文件放在哪

唯一位置，放在框架的本地项目目录下：

```
local/projects/<project-id>/design/design-context.md
```

| 情形 | 路径 |
|---|---|
| 单产品线 | `local/projects/<project-id>/design/design-context.md` |
| 多产品线，或一个独立设计分支 | `local/projects/<project-id>/design/<design-name>/design-context.md`，只写差异，共享层引用上级文件 |
| 页面之间风格不同、功能之间风格不同 | 不新增文件，写进"页面清单"条目 |

不写进业务仓库根目录、不写进任务目录、不复制到多个位置。任务记录与报告只引用路径。

**不创建占位文件。** 框架规则是"暂无某类文档时保留空列表并记录缺口"（见 `core/project-context.md`）；没有设计上下文时不落盘、不登记，等第一次 UI 任务问清后再写。

## 与项目上下文关联

设计上下文是稳定文档，登记在 `local/projects/<project-id>/project-context.yaml` 的 `documentation.development_standards` 下，按需加载：

```yaml
documentation:
  development_standards:
    - path: ./local/projects/<project-id>/design/design-context.md
      load: when_relevant
```

选 `development_standards` 的理由：界面意图最终约束的是开发交付物，与代码规范同属“项目怎么做”的约定，一个入口在 UI 任务里一起加载，不会漏读。

代价与约束：该类别会被读成开发规范，因此本文件必须标明自己是**方向依据**而非硬性规则——权威低于用户当次指令、低于项目既有设计系统与前端规范，其中的"反参考"不得升级成全站禁令。文件内的"执行规范"行就是这条边界的落点。

三类文档不要混放：

| 类别 | 放什么 | 例子 |
|---|---|---|
| `development_standards` | 设计上下文（方向依据）+ 前端规范 / 设计系统（执行规范） | `design/design-context.md`、`docs/ui-kit.md` |
| `business` | 项目目标、使用方式、业务背景 | `README.md` |
| `architecture` | 组件分层、页面结构、路由组织 | `docs/frontend-architecture.md` |

- 同一文档只登记一次；文件不存在时不登记。
- `project-context.yaml` 管"项目在哪、跑什么命令、有哪些稳定文档"；设计上下文管"这个界面的意图"。两者不互相复制内容。
- 若项目已有设计系统或前端规范，本文件**不重复**它，只写一行引用（见模板"执行规范"行）。

## 必填项

| 项 | 要什么 | 不合格 | 合格 |
|---|---|---|---|
| 受众 | 谁用、在什么情境、用多久 | "用户""年轻人" | "凌晨加班从手机上核对库存的门店店长，一只手操作" |
| 用途 | 这一屏要让人完成什么动作或判断 | "展示产品" | "在 20 秒内确认本周哪两个 SKU 会断货" |
| 调性 | 三个词 + 一句解释 | "现代、简洁、高级" | "务实、可靠、不打扰：像一个不多话的老同事" |
| 差异化 | 让人记住的一个点 | "好用" | "首屏就是一张真实门店的俯拍照片，标题压在货架上" |
| 反参考 | 明确不该像什么 | "不要难看" | "任何蓝紫渐变 SaaS 后台、渐变光斑、彩虹图表" |
| 设计原则 | 3–5 条，可自查 | 十条口号 | "结论前置；数字等宽对齐；状态不用颜色单独表达" |
| 品牌资产 | 色、字、logo 能否用；不可用时给替代 | "按品牌来" | "主色 #1f6f43，字族 Noto Sans SC；logo 不用于三处以内" |
| 素材现实 | 自有照片 / 可截真实界面 / 可用图像工具 / 仅纯图形 | "有图" | "无实拍；界面截图可截；不可用图像生成" |

素材现实直接决定门禁 A16 走不走降级，必须写实。

## 两级结构

一份文件里分两层：共享层写所有页面通用的东西；页面清单每条 3–5 行，只写该页特有的。

```markdown
# 设计上下文 · <项目名>

## 共享
- 品牌三词：<词>、<词>、<词>
- 调性：<一句解释>
- 反参考：<列表>
- 设计原则：1) … 2) … 3) …
- 品牌资产：<色值 / 字族 / logo 使用限制>
- 素材现实：<四选一 + 说明>
- 执行规范：以 <tokens.css 或规范文档> 为准，本文件不重复

## 页面清单
### <页面或功能名> · <路由或目录>
- 受众情境：
- 用途（一屏内要完成的动作或判断）：
- 差异化：
- 明确不做：

## 变更
- <日期> <变更人>：<改了什么>｜影响范围：<哪些页面>
```

## 追问方式

- 一次问完，不要边做边问；用户答不上来时给两个具体候选让他选，不继续泛问。
- 用户已给过上下文（历史对话、设计文档）就复用，不重复问。
- 只补一次：回答仍含糊时按最接近的具体候选开工，并在报告写明"按 X 调性执行，若不符请指出"。
- 主体盘点可选补强：列出 8–12 条"只属于这个客户"的事实（门牌、招牌字体、真实数字、它受的限制、它世界里的印刷品）。差异化一项必须能通过"把最近同行代进去是否仍成立"的检验。

## 冲突与变更

- 页面级与共享层冲突：页面级覆盖，但必须在"变更"里写明例外的原因，否则半年后无人说得清。
- 上下文变更不覆盖历史：追加"变更"小节并注明影响范围，避免同一页面混用两版方向。
- 上下文与用户当次指令冲突：以用户当次指令为准，按 `instruction-contract.md` 记录让位。
