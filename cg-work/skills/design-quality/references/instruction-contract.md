# 指令契约

## 目的

解决两件事：用户说"改这里"，结果动了别处；规则与用户指令打架时，执行者用规则压掉用户。契约把"改什么"在动手前固定下来，把"让位"变成可审计的记录。

## 优先级

1. 用户明确指令。
2. 项目自身的品牌与设计规范。
3. 本技能的通用门禁。
4. 执行者的个人审美。

第 1 与第 3 冲突时：**执行用户指令**，记录让位，说明后果。不得争辩，也不得静默放弃规则。

## 改前三行回执

任何 UI 改动前先发这三行；用户说"直接改"时可省略确认，但三行仍要写进任务记录。

```
目标：<一句话，含调性与要解决的具体问题>
会动：<file:selector/token> ×N，逐个列出；没有具体位置就先定位再回执
不动：结构 / 文案 / 数据 / 动效 / 其他页面（逐项确认）
```

判定标准：第三行必须能排除至少一项用户可能担心的副作用；做不到说明还没定位清楚，不许开工。

## 一次一个维度

改动按维度隔离，混改会让"哪一步跑偏"无法归因，这是反复返工的根因。

| 维度 | 包含 |
|---|---|
| 结构 | 区块增删、顺序、栅格、栏数 |
| 排版 | 字族、字号、行高、测度、层级 |
| 颜色 | 底色、墨色、强调、明度台阶 |
| 动效 | 入场、滚动、状态转场、hover |
| 状态 | 空、加载、错误、无权限、hover/focus/disabled |

一轮只做一个维度；需要同时改两个维度时，拆成两次回执。

## 指令不合格时

"更高级""更干净""更好看""有质感"不是可执行指令。处理：把它换成调性词（克制 / 粗粝 / 编辑感 / 玩具感之一）+ 一个具体参照（"像哪个站的那一屏"），再回执。**不猜。**

## 让位记录模板

```markdown
- 让位规则：<门禁编号与名称，如 A10 无渐变>
- 原因：<用户原话或需求约束>
- 影响范围：<哪个选择器/哪个页面，是否会扩散>
- 后果：<可读性/一致性/维护成本上的代价>
- 回滚条件：<什么情况下恢复规则>
```

## 反例

- 用户说"按钮改品牌色"，执行者顺手把整页强调色都换了。→ 越界。
- 用户要求加渐变主按钮，执行者拒绝并解释"AI 味重"。→ 用规则压指令。
- 用户要求加渐变主按钮，执行者加了但没记录，下一轮又按门禁删掉。→ 静默反复。
