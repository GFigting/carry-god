# 项目初始化

## 目标

建立项目与 `cg-work` 之间的最小可靠关联，让后续工作流知道项目位置、规则、技术栈、文档、运行入口和可用技能。

## 执行步骤

1. 读取用户提供的项目根路径；没有明确路径时，使用当前工作区并记录这个判断。
2. 检查项目根路径是否存在、是否为目录，以及是否能识别为项目仓库。
3. 根据项目根目录名生成小写 `kebab-case` 的 `project-id`；重名时追加稳定的仓库或组织标识，并记录判断依据。
4. 探测项目自身的 `AGENTS.md`、`CLAUDE.md`、`README.md`、包管理文件、测试配置、构建配置和文档目录。
5. 识别技术栈、包管理器、测试命令和构建命令；无法确认的字段保持为空并记录缺口，不猜测。
6. 识别启动入口、健康检查、业务文档、架构文档、接口文档、词汇表和项目技能路径。
7. 使用 `core/project-context.template.yaml` 生成 `local/projects/<project-id>/project-context.yaml`。
8. 生成 `local/projects/<project-id>/initialization-report.md`，记录探测范围、事实来源、未确认项、未读取文件、ID 判断和后续建议。
9. 检查所有登记路径是否存在，项目根路径和项目文档路径使用绝对路径。

## 边界

- 不修改项目业务代码、项目规则文件、CI、Git 配置或依赖。
- 不安装依赖、不启动服务、不执行迁移、不创建凭据。
- 不把密钥、令牌、密码、生产数据或完整个人信息写入上下文或报告。
- 不用推测补齐业务规则；不确定内容记录为待确认项。
- 已存在的项目上下文不能直接覆盖，先比较并报告差异，等待确认后再更新；更新时保留上一版上下文和报告中的变更记录。

## 完成标准

- `project-context.yaml` 可读取且项目根路径有效。
- 已发现的项目规则入口和文档路径明确。
- 技术栈、测试和构建命令有事实来源，未知项已记录。
- 初始化报告记录了探测范围、结果和缺口。
- 新上下文或更新后的上下文已经得到用户确认；未确认时保持原上下文不变。
- 后续工作流可以按 `required_context` 和 `skills.paths` 加载项目内容。
