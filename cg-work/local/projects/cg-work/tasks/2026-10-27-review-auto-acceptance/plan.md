# 任务提交后自动验收实施计划

## 目标

把「任务提交（进入 review）后必须等用户验收」改为「满足证据门禁的任务由 Agent 自动验收标记 done」，消除验收积压；不满足门禁的任务保持 review 并明确用户动作。

## 需求理解

用户原话：「框架优化：任务提交了自动验收任务」。按「任务提交后自动验收该任务」理解：现状只有 `delivery_path: lightweight` 且单模块、不改业务规则/接口/数据/权限的任务可自动收尾，其余全部滞留 review（当前待验收清单 14 条，其中 12 条等待用户）。本任务将该例外扩展为统一的「自动验收门禁」。

## 范围

### 包含

- 新的 review 阶段自动验收规则（替换 lightweight-only 例外），统一写在 `core/operating-model.md`，README 与 workflows 改指针或同步口径。
- 自动验收的强制证据要求：状态历史与验证记录写明自动验收依据。
- 版本号升级（新增兼容能力 → 次版本）。

### 不包含

- 不修改 `acceptance-queue.mjs`、`task-stamp.mjs` 等脚本行为（队列仍列出 review 任务，用户仍可批量验收）。
- 不触碰特殊操作授权边界（生产、外部、破坏性、认证、部署）。
- 不处理各业务项目滞留任务本身的验收结论（存量按新规则核对见测试用例 TC-004）。

## 需求与验收

- 需求来源：用户会话指令「框架优化：任务提交了自动验收任务」
- 自动验收门禁（新规则正文草案）：任务完成 review 统一收尾后，同时满足以下全部条件时由 Agent 执行自动验收并更新为 `done`：
  1. 每条验收标准（`acceptance_summary` 或 plan.md 测试用例清单）均有新鲜通过证据并回写验证记录；
  2. 无未决决策、无需用户取舍的事项；
  3. 验证结论中不存在「环境受限未执行」项（「不适用」须注明理由）；
  4. 不涉及生产执行、不可逆外部副作用、凭据或权限变更、数据迁移/删除/语义转换（特殊操作边界不变）。
  任一条件不满足时任务保持 `review`，`next_action.required: true` 写明用户需要的动作。自动验收必须在 `status_history` 与验证记录中写明「自动验收」依据和证据，不得静默标记。
- 验收标准：
  - [x] `core/operating-model.md` 收尾第 6 步与「待验收清单与批量验收」节按新门禁改写，README 步骤 8、`workflows/review.md`、`workflows/framework-optimization.md` 口径一致（唯一来源 + 指针，无双来源）
  - [x] 旧口径「其他任务必须完成用户验收后才能更新为 done」「不得适用自动完成例外（业务规则/接口/数据/权限）」在活跃规则正文中零残留或已改写为新门禁表述
  - [x] 主任务（`role: parent`）关闭仍要求用户验收，不适用自动验收
  - [x] `VERSION` 次版本升级；`npm run check` 与 `npm test` 全绿
  - [x] 现有 review 滞留任务按新门禁逐条核对：证据齐全者自动验收，缺口者保持 review 且 next_action 明确

## 影响范围

- 文件、模块、接口或数据：`README.md`、`core/operating-model.md`、`workflows/review.md`、`workflows/framework-optimization.md`、`VERSION`
- 调用方和依赖方：`skills/subagent-dispatch-timing`（验证派发口径，预计仅指针核对）、`scripts/README.md`（归档不等于验收的表述保持）、各业务项目滞留任务记录

## 实施步骤

1. 决策预检：向用户确认三个决策点（见「计划审核-待确认决策」），确认后转 `in_progress`。
2. 改写 `core/operating-model.md` 收尾第 6 步与「待验收清单与批量验收」节为统一自动验收门禁。
3. 同步 `README.md` 步骤 8、`workflows/review.md`、`workflows/framework-optimization.md` 口径（core 为唯一来源，其余改指针或简短一致表述）。
4. `VERSION` 次版本升级。
5. 运行 `npm run check`、`npm test`，执行 TC-003 残留检查。
6. 按新门禁逐条核对现有 review 滞留任务并回写状态与依据（TC-004）。

## 计划审核

- 需求覆盖：按「提交后自动验收」理解覆盖；若用户实际诉求为「提交时自动派发验收取证」或「收紧自动标记 done」，本计划作废重做（见待确认决策 D0）。
- 范围边界：不改脚本行为、不碰特殊操作边界，无越界。
- 依赖与顺序：步骤 2 为唯一来源先行，3/4 随后，5/6 验证与存量处理。
- 验收与验证：全部可观察（check/test/grep/queue）。
- 风险与回滚：主要风险是自动验收削弱用户把关；以门禁 4 项 + 强制留痕兜底，回滚即还原规则文档。
- 审核结论：待用户确认后通过。
- 审核意见来源：主 Agent 自审 + 用户决策。

### 待确认决策

- **D0 需求方向**：本计划按「任务提交后满足门禁即自动验收 done」设计；若你指的是「提交时自动派发验收取证（仍由你验收）」或「收紧现有自动标记 done 的滥用」，请指出，任务将重定向。
- **D1 门禁范围**：改变业务规则/接口/数据/权限的任务，只要证据齐全、无未决决策，是否也允许自动验收？（推荐：允许——否则现有 fms/lasen 业务任务积压仍解不掉；风险由「新鲜证据 + 强制留痕 + 特殊操作边界」兜底）
- **D2 主任务**：`role: parent` 主任务关闭是否保留用户验收？（推荐：保留，主任务承载集成结论，不适合自动验收）
- **D3 存量追溯**：新规则生效后，是否立即对当前 14 条待验收清单逐条按门禁核对并自动验收合格项？（推荐：是；不合格项保持 review 并补明确 next_action）

## 验证

- 自动化测试：`npm test`
- 静态检查或构建：`npm run check`
- 页面、接口或用户验收：`npm run queue` 输出对照新门禁逐条核对

## 风险与交付

- 风险和环境限制：自动验收把「done」的裁量权部分移交 Agent，误判风险由证据门禁与留痕约束；存量核对阶段若发现证据造假类问题须停止并回报。
- 集成方式：规则改动与 cg-work 记录分 commit，本地提交，推送需另行授权。
