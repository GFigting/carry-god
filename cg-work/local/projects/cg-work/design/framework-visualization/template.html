框架地图

五大目录各唯一职责；规则正文以 README.md 与 core/ 为唯一来源，本页不复制规则、只做导航。

AGENTS.md · README.md

路由与唯一推荐入口：项目识别门禁 → 项目上下文 → 低风险判断 → 任务记录 → 技能加载 → review 收尾 → npm run check。

core/

规则正文唯一来源：工作模型（状态机/证据生命周期）、项目上下文、命名与提交、框架维护、特殊操作授权边界 + 模板。

workflows/

按开发意图的 8 个流程，共享同一阶段契约；技能引用分 framework: / project: 两类。

skills/

个技能：。原始镜像保持上游原样，不做本地改写。

scripts/

结构/锚点/镜像一致性校验与任务工具：check、queue、archive、migrate、task-stamp。

local/

个受管项目的上下文、需求箱与任务产物；业务项目真实数据保持本地不入库。

规则优先级（冲突时自上而下）

用户明确要求> 项目自身规则> core/> workflows/> skills/ 建议

提交口径

框架内容默认全部提交；业务项目数据、需求、任务与报告保持本地。收尾只建本地 commit；推送/合并/部署需单独授权。

使用顺序（README 十步）

  1. 读入口：AGENTS.md + README.md
  2. 项目识别：framework:project-discovery
  3. 上下文检查：缺失则 project-initialization
  4. 低风险判断：纯文案/样式走免记录路径
  5. 建任务：其他变更创建 pending task
  6. 加载技能：按流程声明 required skills
  7. 决策预检：高风险等待用户确认
  8. 证据留痕：计划/审查/验证分阶段落盘
  9. 校验：npm run check / npm run queue
  10. 授权边界：外部/破坏性操作先读 special-operations

任务状态机

来源 core/operating-model.md：主链路 pending → in_progress → review → done；blocked / cancelled 为异常状态，done 与 cancelled 为终态。

主链路 / 回退 异常与取消 异常状态（虚线框） 点击节点查看门禁与出入边

允许的状态转移

当前状态可转移到
pendingin_progress · blocked · cancelled
in_progressreview · blocked · cancelled
reviewin_progress · done · blocked · cancelled
blockedpending · in_progress · cancelled
done无（终态，后续变更建新任务）
cancelled无（终态，重启建新任务）

门禁要点

  1. 不得跳过 review 直接进入 done
  2. review 需审查记录 + 新鲜验证证据；声明原型的还需原型采纳记录
  3. done 需用户验收（轻量自动完成条件除外）
  4. 验证失败/审查有问题回 in_progress，不设 revision 状态
  5. review/blocked/done 时必须维护 next_action（required/action/message）

工作流与交付路径

工作流按开发意图选择；交付路径按影响面与风险选择，不按任务名选择。次数列为任务记录中的实际引用统计。

工作流使用场景关键门禁引用次数
project-discovery上下文加载前判断既有项目 / 新项目 / 信息不足唯一匹配自动路由，其余确认后路由–
feature-development新功能和行为变更小功能可走轻量执行；新业务规则/接口须独立验收–
low-risk-change纯文案、样式、静态布局、可访问性标记免记录路径；任一低风险条件不满足即升级–
bugfix缺陷、回归和性能问题根因已确认且仅恢复既有行为–
refactor保持外部行为的结构调整行为不变，验证绑定交付点–
review代码、变更和交付前审查统一收尾六步：验证→测试→冗余→文档→清单→集成–
framework-optimization框架规则、流程、模板、校验器与自有技能演进框架自身维护约束优先–
parent-child-decomposition跨模块 / 跨会话 / 未决关键决策的大需求主任务 role: parent，子任务 parent_reference 挂靠–

轻量执行决策清单（任一项为「是」即进入标准执行）

  • 是否跨模块（改动或验证超出单一模块/业务边界）？
  • 是否改变业务规则、接口、数据或权限？
  • 是否存在迁移、删除或其他不可逆写入？
  • 是否有未决业务决策？
  • 是否产生外部副作用？
