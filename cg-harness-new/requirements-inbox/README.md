# 需求收件箱

需求收件箱是外部需求文件包进入框架的统一入口，支持一个需求包包含原型、需求文档、截图、表格和其他附件。需求材料按项目隔离保存。

## 目录结构

```text
requirements-inbox/
├── README.md
├── {项目标识}/
│   ├── {需求包名称}/
│   │   ├── README.md          # 可选：来源、背景和联系人
│   │   ├── 需求文档.md
│   │   ├── 原型.html
│   │   └── ...                # 图片、表格、附件等
│   └── _processed/            # 该项目已确认归档的原始需求包
└── _unassigned/               # 项目归属尚未确认的需求包
```

项目标识使用 `registry/project-context.yaml` 中的项目键。每个项目目录下的一级子目录是一个独立需求包；多个需求可以同时放入收件箱，互不覆盖；同一需求的所有材料应放在同一个需求包内。

## 入站流程

1. 明确项目后，将外部需求包整体复制到 `requirements-inbox/{项目标识}/`，不能拆散原型和配套文档；项目不明确时放入 `_unassigned/`。
2. Agent 逐个项目、逐个需求包读取材料，输出需求摘要、验收标准、未知项和归属建议。
3. 对所有需求包生成分诊汇总，建议新建任务、追加现有任务或搁置，并标注依赖与冲突。
4. 人工确认归属和范围；Agent 不得自动批准或自动改变现有任务目标。
5. 确认后的需求包移动到 `requirements-inbox/{项目标识}/_processed/{需求包名称}/`，原始材料保留，不自动删除。

## 报告产物

每个需求包的分诊、分析、计划和验证证据保存到 `reports/{项目标识}/{需求包名称}/`。原始需求材料始终保留在对应项目的收件箱或 `_processed/`，不与分析报告混放。报告目录结构、命名和迁移规则遵循 `reports/README.md`。

## 出站流程

需要交给框架外部人员时，将已确认任务导出为独立文档包放入本目录。导出包应去除框架内部任务编号、路径和宿主细节，并附带面向业务读者的 README。

## 并行需求规则

- 按项目、需求包逐包建立 intake 记录；一个包不能覆盖另一个包的分析结果。
- 有依赖的需求仍分别记录，在汇总中声明 `depends_on`，由技术负责人决定处理顺序。
- 发现重复或冲突时先标记为“待确认”，不得静默合并。
- 只有完成项目和需求归属确认的需求包才能移动到对应项目的 `_processed/`。
- `_unassigned/` 中的需求包不得直接进入项目报告目录；确认项目后先移动原始材料，再建立项目报告。
- `_processed/` 中按原需求包名称保留历史，必要时在包内增加分析记录和确认记录。
