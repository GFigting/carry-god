# 提交规范

## 适用边界

本规范定义通用 Git 提交格式和质量要求。项目自身的分支模型、提交类型、Issue 编号、签名、Hook 和 CI 规则优先；与本规范冲突时记录采用的项目规则。

## 提交粒度

- 一个提交只表达一个可审阅、可验证的目的。
- 行为变化、纯重构、格式化、依赖升级和生成文件应分开提交，除非拆分会使任一提交无法构建、测试或理解。
- 不提交无关文件、临时调试代码、本机配置、凭据、令牌或敏感数据。
- 提交前检查工作区差异，确认没有遗漏必要文件或混入他人的无关变更。

## 标题格式

```text
<type>(<scope>): <summary>
```

- `type` 必填，使用下表中的英文类型。
- `scope` 可选，表示受影响模块或业务边界；没有清晰范围时省略括号。
- `summary` 必填，使用简洁中文描述结果，不加句号，建议不超过 30 个汉字。
- 标题说明“做成了什么”，不写“修改代码”“处理问题”等无信息描述。

## 类型

| 类型 | 使用场景 |
| --- | --- |
| `feat` | 新增对外可见能力或行为 |
| `fix` | 修复错误、回归或不符合预期的行为 |
| `refactor` | 保持外部行为不变的结构调整 |
| `perf` | 性能改进 |
| `test` | 新增或调整测试，且不改变生产行为 |
| `docs` | 文档、流程或说明变更 |
| `build` | 构建、依赖或打包配置变更 |
| `ci` | 持续集成或自动化流水线变更 |
| `chore` | 其他不影响生产行为的维护工作 |
| `revert` | 撤销已有提交 |

## 正文格式

默认只写标题。标题无法完整表达修改内容时，在标题后空一行补充正文。

```text
<修改内容、关键实现或影响范围>
```

- 正文只介绍修改内容、关键实现或影响范围，不重复标题。
- 任务关联、验证结果和风险仍记录在任务记录、报告或交付摘要中，不写入提交正文。

## 示例

```text
feat(requirements-inbox): 支持批量需求分诊
```

```text
fix(sync): 空参数任务默认增量同步

主体和供应商定时任务在空参数时显式选择增量同步。
```

## 提交前门禁

- [ ] 标题符合格式，类型和范围与实际变更一致。
- [ ] 提交只包含一个可审阅目的，且没有无关变更。
- [ ] 已使用项目配置的格式化工具格式化受影响代码；格式化后已复查差异，没有混入无关文件或全仓格式化噪声。
- [ ] 已执行与风险相称的测试、静态检查或真实路径验证。
- [ ] 需要正文时，正文只说明修改内容、关键实现或影响范围。
- [ ] 没有凭据、敏感数据、本机配置或未经授权的生成产物。
- [ ] 审查发现已修复，或有明确记录的延后项。

项目未提供格式化命令时，先查阅项目约定和现有脚本；仍无法确定时，记录该缺口，不得擅自引入新的格式化工具或改写无关文件。

## 例外

- 紧急回滚可以使用 `revert` 并简述被撤销的提交与原因；验证受环境限制时必须如实记录。
- 项目要求 Squash Merge、Rebase Merge 或自动生成提交信息时，保留本规范的语义字段，具体命令和格式遵循项目规则。
