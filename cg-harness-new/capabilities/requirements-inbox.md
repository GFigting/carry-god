# 需求收件箱

## 目标

把包含原型、需求文档和附件的多文件需求包，转换为可确认、可追踪的需求接入结果；支持同一批次处理多个需求，同时保持每个需求包的边界。

## 输入

- `requirements-inbox/` 下的一级需求包目录。
- 需求包内任意受支持的文本、原型、图片、表格或其他附件。
- 可选的项目上下文、现有 Goal/Task 索引和领域词汇表。

## 处理步骤

1. 先按项目标识分组，再枚举每个项目下的需求包，并为每个包建立独立的 intake 记录；项目不明确的包进入 `_unassigned/`。
2. 读取 README、需求文档、原型和附件的可观察内容，记录无法读取的文件。
3. 提取目标、用户、范围、非目标、约束、验收标准、术语和未知项。
4. 建议归属：新建任务、追加现有任务或搁置；如有依赖、重复或冲突，单独标记。
5. 输出批次汇总，但不因批量处理而合并独立需求，也不替人工确认。
6. 人工确认后，将原始需求包移动到 `requirements-inbox/{项目标识}/_processed/`，并保留分析和确认记录。

## 输出

- 每个需求包一份 `reports/{项目标识}/{需求包名称}/intake.md`，使用 `templates/requirements-inbox-intake.md`。
- 一份批次汇总，列出需求包、建议归属、依赖、冲突和待确认项。
- 确认后的任务记录或对现有任务的追加说明。
- 归档路径和移动前后的验证结果。

## 规则

- 一个一级子目录就是一个需求包；不要按文件分别创建任务。
- 未确认前只允许分析和建议，不得修改现有任务目标或移动原始文件。
- 技术细节的可信度低于代码库实际证据；原型和文档表达业务意图，不替代实现依据。
- 发现同名、重复或相互冲突的需求时保留原文，标记待确认，不静默覆盖。
- 移动需求包属于可审计的文件操作：先确认目标路径，再检查源目录不存在遗漏。

## 验收标准

- 能同时识别两个或更多独立需求包，并分别产生 intake 记录。
- 一个需求包内的 HTML、Markdown、图片和表格仍被视为同一组材料。
- 汇总结果能表达新建、追加、搁置、依赖和冲突。
- 未经人工确认不会归档或改变任务目标。
- 归档后原始文件仍可恢复，且路径可追踪。
