# 通用代码实现规范

## 适用边界

本规范适用于不依赖具体语言、框架、项目目录或业务领域的代码实现。项目自身的编码规范、架构约束和安全策略优先；两者冲突时记录采用的项目规则。

## 代码结构

- 先搜索现有实现、公共工具、类型和测试，再决定新增或抽象。
- 一个模块、函数或类保持清晰且完整的职责，避免把无关行为聚合在一起。
- 接口表达业务动作或稳定能力，不暴露调用方不需要的内部步骤。
- 优先小而稳定的接口，减少不必要的参数、隐式状态和跨模块依赖。
- 变更保持聚焦，不在同一改动中夹带无关重构或格式化噪声。

## 命名与可读性

- 名称表达意图，避免无意义名称、过度缩写和依赖上下文才能理解的简称。
- 布尔值、状态和动作使用能体现语义的名称；避免用 `data`、`info`、`handle` 等泛化名称掩盖真实含义。
- 控制流程优先保持直线可读；复杂条件提取为有意义的判断函数或领域规则。
- 注释解释原因、约束、兼容性或非显然决策，不重复代码表面行为。

## 输入与边界

- 所有外部输入都视为不可信，明确校验类型、格式、范围、权限和业务状态。
- 明确处理空值、缺省值、重复请求、超限、非法状态和资源不存在等边界。
- 公共接口的成功、失败、重试、超时和幂等行为应有稳定约定。
- 不用静默兜底掩盖数据缺失；兜底行为必须有业务理由并可被验证。

## 错误与日志

- 错误应在最接近可判断的位置处理，保留足够上下文，避免静默吞错。
- 对外错误信息给出可执行的反馈；内部日志记录定位所需的标识、阶段和失败原因。
- 日志不得包含密码、令牌、密钥、完整个人信息或不必要的敏感业务数据。
- 重试必须有边界、退避或终止条件，避免失败放大和重复写入。

## 数据与并发

- 写操作明确事务边界、一致性要求和失败后的恢复方式。
- 可能重复执行的接口、任务和消息处理必须设计幂等键或等价保护。
- 并发更新时明确冲突策略，不能依赖偶然的执行顺序。
- 数据结构变化要说明兼容旧数据、旧调用方和回滚的方式。

## 测试与验证

- 每个行为变化都有对应测试或可重复的反馈检查。
- 测试优先验证公开行为和真实边界，不绑定不必要的内部实现细节。
- 至少覆盖成功、失败、空数据、边界输入和重复执行中与本次变更相关的场景。
- 修改测试预期时，记录这是有意的行为变化，而不是迁就实现。
- 先运行局部验证，再按影响范围扩大；完成声明必须基于本轮实际结果。

## 实现完成检查

- [ ] 已查找并遵循项目自身规范。
- [ ] 变更范围聚焦，没有无关重构。
- [ ] 公共接口、边界和错误行为已明确。
- [ ] 外部输入、权限、敏感数据和危险操作已检查。
- [ ] 相关测试或反馈检查已运行并记录结果。
- [ ] 已知限制、兼容性影响和剩余风险已记录。
