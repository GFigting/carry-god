# 独立代码审查

审查以实际差异、验收标准和项目约定为基准。审查报告应帮助决策，不以猜测、泛化建议或对代码作者的复述代替证据。

## 适用条件

重要功能完成后、合并或交付前、复杂缺陷修复后、重构前后，或用户明确请求审查时。审查不自动授权修改代码；修复仍须遵循任务状态和计划确认门禁。

## 审查准备

1. 锁定审查基线：任务记录或 `AC-*`、比较提交或文件清单、项目约定和本轮验证证据。
2. 明确已审查范围与未审查范围。基线不明确时，只能报告可见差异，不得宣称全量通过。
3. 对复杂或高风险变更，优先由未参与实现的审查者执行；审查输入只提供任务目标、范围、约束、差异和证据，不转交无关对话历史。

## 审查步骤

1. 对照验收标准检查实现路径、失败路径和未授权行为变化。
2. 检查边界、错误处理、安全、数据完整性、兼容性、性能、可维护性和测试覆盖。
3. 核对每项测试或验证证据实际覆盖的行为，不以“已有测试”推断所有场景已通过。
4. 将发现按严重性排序：阻断交付、需要修复、建议改进或已接受的取舍。
5. 每条发现必须核对位置、现有行为、影响、复现或推理证据；无法核实的观察标为问题或风险，不作为缺陷。

## 反馈处理

1. 收到审查意见后，先逐项确认其是否适用于当前代码、项目约定和已确认范围。
2. 描述不清、与既有决策冲突或可能扩大范围的意见，先澄清或提交人工决策，不做部分猜测式修复。
3. 已确认的阻断项和需要修复项逐项处理并重新验证受影响范围。
4. 不采纳的意见必须记录技术依据；延后项必须记录原因、影响和后续任务。

## 输出

由已加载的代码审查 capability 指定报告模板；输出审查基线、覆盖范围、发现、证据、处理结论和剩余风险。结论只能是“通过”“需要修复”或“带明确延后项通过”。
