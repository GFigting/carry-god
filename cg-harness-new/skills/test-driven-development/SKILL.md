# 测试驱动开发

对可自动化验证的行为变更，先写测试或可重复反馈检查，确认其因缺少目标行为而失败，再写最小实现使其通过。

## 适用条件

新功能、缺陷修复、行为变更和高风险重构。项目未提供自动化测试能力时，使用最小可重复检查，并在任务记录中说明限制。原型、生成文件、纯配置或无法自动化的变更，是否例外由任务范围和人工确认决定。

## 红绿重构循环

### RED：表达预期行为

1. 选择一个最小验收切片或已复现缺陷。
2. 编写只表达一个行为的测试，名称说明输入、动作和可观察结果。
3. 优先断言真实行为；只有隔离外部依赖确有必要时才使用模拟对象。

### 验证 RED

1. 使用项目既有的测试命令运行目标测试。
2. 确认测试是失败而非执行错误。
3. 确认失败原因是目标行为尚未实现或缺陷尚未修复，而不是拼写、环境或测试夹具错误。
4. 测试直接通过时，确认行为是否已存在；若未覆盖目标场景，修正测试后重新验证失败。

### GREEN：最小实现

1. 只实现让当前测试通过的必要行为。
2. 不在同一切片内添加未被验收标准要求的选项、抽象或无关改造。
3. 运行目标测试，并按风险运行受影响的相邻测试。

### REFACTOR：保持绿色

仅在测试通过后清理重复、命名和局部结构。每次重构后重新运行相关测试；行为变化回到下一个 RED 切片。

## 质量检查

- 每个测试只证明一个行为，覆盖成功、失败或边界中的相关场景。
- 测试应说明对外行为，不依赖实现细节。
- 难以测试通常表示接口、依赖或职责边界需要简化；先记录设计问题，再决定是否调整设计。
- 修改既有测试预期时，必须记录对应 `AC-*` 或已确认行为变化的理由。

## 输出

每个切片的失败证据、实现路径、通过结果、覆盖范围和不能自动化验证的限制。
