# 系统化缺陷调试

在提出修复方案前，先取得根因证据。症状缓解、扩大超时、吞掉异常或绕过断言不能代替根因修复。

## 适用条件

缺陷、回归、测试或构建失败、性能异常、间歇性故障和多组件集成异常。执行前先满足 `workflow/software-delivery.md`、项目上下文与任务确认要求。

## 调试循环

### 1. 根因调查

1. 完整读取错误、警告、堆栈、退出状态和关联日志。
2. 固化最小复现：输入、环境、步骤、预期和实际结果；不能稳定复现时，记录采样计划，不猜测修复。
3. 核对近期代码、依赖、配置、数据和环境差异。
4. 多组件链路在边界收集输入、输出、配置传播和状态证据，定位首个失效边界。
5. 逆向追踪异常值、调用链或状态变化，直到找到可验证的来源。

### 2. 模式分析

1. 查找同仓库中相近且正常工作的实现。
2. 对照项目约定、接口契约和依赖前提。
3. 列出正常与异常路径的可观察差异，不凭经验排除细小差异。

### 3. 假设验证

1. 写明单一假设：根因是什么，以及哪项证据支持它。
2. 以最小、可回退的探针或测试验证该假设，一次只改变一个变量。
3. 假设不成立时，记录结果并回到调查阶段；不得在失败假设上叠加修复。

### 4. 修复与回归

1. 为缺陷添加失败的回归测试或等价的可重复反馈检查。
2. 仅修复已验证的根因，不捎带进行无关重构。
3. 运行回归测试和受影响范围的验证，回填任务记录中的命令、结果和残余风险。

## 停止与升级

- 连续两次修复假设失败：停止修改，回到根因调查。
- 已有三次失败修复，或每次修复暴露不同的共享状态、耦合或边界问题：暂停实施，记录架构风险并请求人工确认后再改变方案。
- 根因确认属于外部服务、环境或时序问题时，记录已排除项、可观测证据、缓解措施和再次验证条件。

## 输出

症状、复现步骤、根因假设与证据、排除项、修复范围、回归验证、残余风险和下一步行动。
