# 软件交付流程

## 阶段

### 1. 需求接入

需求可以来自 `requirements-inbox/{项目标识}/` 下的一个或多个需求包，也可以暂存于 `_unassigned/`。按项目、需求包逐个明确目标、用户、范围、非目标、约束、成功标准和未知问题，再汇总依赖、重复和冲突。需求不成熟时先澄清，不直接编写实现计划；未经人工确认不得归档需求包或改变已有任务目标。

先判断原型是否适用：新页面、复杂交互、流程状态、布局密度或视觉方案存在较大不确定性时，要求原型或等价的交互设计证据；后端接口、数据模型、SQL、权限、定时任务、性能和内部重构不因没有原型而阻塞，改用接口契约、数据定义、项目规范或既有实现作为依据。存在原型时必须登记唯一有效版本和适用范围；原型只作为相关页面和交互的验收依据，不扩展为所有任务的必需材料。

需求确认后必须建立需求到开发的追踪基线：为每条验收标准分配稳定编号（如 `AC-01`），补充至少一个成功、失败或边界场景，并记录来源证据。开发任务只能引用已确认的 `AC-*`，不得只引用需求标题或口头描述。

### 2. 方案设计

识别领域对象、系统边界、接口、数据流、失败模式和兼容性影响。优先设计小接口、清晰边界和可通过接口测试的模块。

### 3. 计划

把方案拆成可独立验证的垂直切片，标注每个切片覆盖的 `AC-*`、输入、输出、依赖、风险、文件范围、测试策略和完成标准。计划必须单独输出，并显式区分默认判断和待人工确认决策：成熟业务惯例、已确认原型、既有实现证据以及不影响核心业务的数据结构或交互细节，可由技术负责人默认采用；业务规则、权限、数据兼容、流程状态、跨系统契约和可能导致明显返工的取舍，必须列为待人工确认。确认记录形成前，计划只能调查、分析和完善，不驱动代码修改。若某条 `AC-*` 没有切片或验证方式，计划不能进入 `ready`。

跨前后端、数据模型、接口或高风险变更，技术负责人应在必要时安排独立智能体复核计划。复核只检查范围、依赖、风险和验收标准，不决定业务方案、不修改代码；技术负责人负责整合复核结果并输出唯一的最终计划，等待人工确认。

### 4. 实施

仅在计划已经人工确认后，按最小垂直切片推进，先加载 `capabilities/code-implementation-standards.md` 和项目自身约定，建立失败测试或可观察的反馈环，再实现、重构和补齐边界。每一步都保留变更和验证证据，并在任务记录中回填实际代码路径、测试名称和结果；发现需求变化时回到需求基线，新增或修改 `AC-*` 后重新确认计划再继续实施。

### 5. 审查与验证

分别检查是否满足需求、是否符合项目标准、是否覆盖风险。按追踪基线逐条核对 `AC-* -> 场景 -> 切片 -> 代码 -> 测试 -> 结果`，任何缺口都必须修复或明确记录为延后项。准备提交时加载 `capabilities/commit-conventions.md`，确保提交范围、标题和验证证据可审阅。修复审查意见后只重新验证受影响范围，并保留完整结果。

### 6. 交付与沉淀

确认验收标准、测试结果、人工复查事项、部署或回滚注意点，并把通用经验沉淀为项目文档或框架能力。完成任务有文件变更时，按项目完成 Git 提交，并将去重、优化后的任务文本登记到统一完成记录文件；具体规则见 `workflow/completed-task-records.md`。

## 缺陷修复与重构专用门禁

缺陷修复和重构不能直接进入实施阶段，必须遵循：

```text
收集现状 -> 生成 Markdown 报告 -> 确认范围与方案 -> 修改代码 -> 回归验证 -> 更新报告
```

Markdown 报告是前置分析产物，不是事后总结。它必须说明现状证据、影响的前端/后端/数据链路、领域术语、候选方案和验证计划。

## 阶段结束规则

每个阶段结束时，任务记录和回复都必须给出下一步行动。若无法继续，必须明确是等待用户确认、等待外部依赖、等待测试环境，还是需要重新澄清需求。
